# Mode: import

Before anything else in this mode, run the **Trigger check** in [SKILL.md](../SKILL.md).

Bring old resumes, CVs, LinkedIn exports, bios or reports into the log. Different versions describe the same experience in different words and contexts; the job is to merge them into one entry per experience without inventing anything. The originals stay unchanged in `sources/`, so nothing is lost when an entry keeps each wording only once.

When the source is an AI chat history (a ChatGPT, Claude.ai or Gemini export, or Perplexity), follow [import-chats.md](import-chats.md) instead of steps 1–2: the raw export stays out of git and only the conversations the user picks are copied. When it is another logged-in website (a LinkedIn profile), first follow [import-web.md](import-web.md) to capture it into `sources/<origin>/`, then continue from step 3 with those files.

1. **Collect and preserve the originals.** Take every file in `sources/inbox/` (or the files the user handed over, copied there first). Move each, unchanged, to `sources/resumes/<YYYY-MM-DD>-<label>.<ext>` (the document's date when it gives a day, otherwise the import date, with the document's own date noted in the report) if it is a resume or CV, otherwise to `sources/<origin>/` (e.g. `linkedin/`) with the same naming. Ask the user for a document's date or target role only when the file and its name do not show it.
2. **Extract text.** `.md`/`.txt`/`.tex`: read directly. `.docx`/`.rtf`/`.doc`: `textutil -convert txt -stdout <file>` on macOS, `pandoc -t plain <file>` elsewhere. `.pdf`: the Read tool. Check each extraction is complete before moving on.
3. **Split into items.** For each document list every experience item (job, internship, project, research, leadership, award, course), plus profile facts (contact, education, skills, languages).
4. **Match items across documents and against existing entries.** Same organisation and overlapping period is a match; for projects, the same project under a different title or framing is a match too. Classify each item as **match**, **new**, or **ambiguous**. Put every ambiguous case to the user in one numbered round with your proposed answer, and wait. Ask in the same round for any new item's start month when no document gives one; without an answer, the document's month names the file (step 5's `--month`) and the period is `GAP – YYYY-MM` (or `GAP – GAP` when the end is unknown too).
5. **Merge into entries.** For each experience:
   - Create a new entry with `python3 -I <root>/tools/entries.py new <slug> --root <root> --month <YYYY-MM> --status imported --field title=<title> --field period=<period>`, adding a `--field <name>=<value>` for each other front matter field the documents give; the tool writes `GAP` in the rest and the entry's `README.md` row. `--month` is the start month, or step 4's document month. Pass `--field visibility=<value>` only when a document settles it (a personal project in a public repo: `public`, cited by the repo; work the document calls confidential or under NDA: `nda`, cited by the document) or the user says which during the import, with its source as `--field-source visibility=<repo URL>` (or the document's path, or `"user, YYYY-MM-DD"`). A field the user states during the import, of those *Provenance* in [SKILL.md](../SKILL.md#rules-for-every-mode) names, cites them the same way, `--field-source <name>="user, YYYY-MM-DD"`. When this step changes an existing entry's title, period, type or tags, run `python3 -I <root>/tools/entries.py readme-row <entry> --root <root>`.
   - Add each bullet, verbatim, with `python3 -I <root>/tools/entries.py phrasing-add <entry> --root <root> --angle <angle> --source <source file> -- "<bullet>"`, the angle the resume target it suits (as `entries/_template.md` defines it), the newest document first: a bullet repeated word for word then keeps one line, citing the newest version. On its `similar:` lines, judge: the same bullet in other words is rerun with `--replace <n>` (the line number the `similar:` line gives) when this document is newer than the one that line cites, and dropped otherwise; a different claim is rerun with `--distinct`. Consolidate trims the section to two per angle.
   - Lift facts (dates, titles, numbers, technologies, outcomes) into the matching sections, each with provenance `(sources/resumes/<file>)`.
   - Record contradictions between versions (different dates, numbers, titles, scope) under `## Conflicts`, as a line starting `Open:` that quotes each side with its source. Leave them unresolved for consolidate, unless the user rules on one during the import (then settle it as consolidate step 2 says).
   - Leave every section the documents cannot fill as `GAP:`.
   Merge profile facts into `profile.md` the same way.
   Then deny the names of each entry file this step created or changed, as [commits.md › Names appended to `.export-deny`](../commits.md#names-appended-to-export-deny) says.
   A value for a Direction item or a Config field (`python3 -I <root>/tools/config.py fields` lists them: a resume's objective naming a target role, a visa, citizenship or "no sponsorship required", a sorting order, a record language) goes only into the import report, under *Found for setup*, with its source: `direction.md`'s items and `config.toml` change through setup alone. Step 7 offers each one.
   For any story an imported item could tell (a hard bug, a lead role, a conflict), run `python3 -I <root>/tools/entries.py story-add "<question type>" <entry>#<section anchor> --marker raw --summary "<one line>" --root <root>`, with the anchor of the section that holds its facts: its heading lowercased, spaces as `-`, and every character other than a letter, digit, `-` or `_` dropped (`## Decisions and trade-offs` is `#decisions-and-trade-offs`).
6. **Write the import report** as a new section in `sources/import-log.md`: files imported; entries created and updated; conflicts found; *Found for setup* (step 5); and, per entry, its `state:` line from `python3 -I <root>/tools/entries.py state <entry>... --root <root>` (its `GAP` count) and which entry to consolidate first. The gaps themselves stay in the entries, where answering one removes it. A fact or ruling the user gives during the import goes into its entry with `(user, YYYY-MM-DD)`, never only into this report.
7. **Show the report**, then commit as [commits.md › Bulk data changes](../commits.md#bulk-data-changes) says: `import: <n> file(s), <m> entr(y/ies)`, each noun in the singular or plural its count takes (1 file, 2 files; 1 entry, 0 entries). On a yes, offer each *Found for setup* value, one at a time, through [setup › Changes](setup.md#changes). On a no, offer none: the discard took the report they came from, and running the import again finds them again. The `.export-deny` lines step 5 committed stay either way, because they are committed outside the yes or no ([commits.md › Names appended to `.export-deny`](../commits.md#names-appended-to-export-deny)); after a no, tell the user so in one line, since that commit names entry files that no longer exist.
8. **Next up**, once the user has answered step 7's offers (none after a no, or when *Found for setup* is empty): run the command [SKILL.md › Next up](../SKILL.md#rules-for-every-mode) gives, with `import`.

Done when the user has answered step 7's bulk change, yes or no, and:
- **yes:** every file in the inbox is preserved where step 1 puts it, every item from every document is either in an entry or listed in the report as deliberately skipped (with the reason), and every conflict is recorded; the change is committed and pushed; and each *Found for setup* value has been offered.
- **no:** every original step 1 moved is back in `sources/inbox/` under its old name, and `python3 -I <root>/tools/sync.py status` prints `log changes: none`.

Either way, the last message ends with the Next up block.
