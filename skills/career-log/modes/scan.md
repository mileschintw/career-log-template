# Mode: scan

Before this mode's first step, run the **Trigger check** in [SKILL.md](../SKILL.md).

Collect new postings from the user's job sources, drop the ones already applied to or declined, screen the rest, fit the best of them, rank them, save a report, and, when asked, draft a resume and answers for the best few on a throwaway branch. It runs by hand ("scan", "any new postings?") or as a scheduled task (*Schedule*). The user applies: the agent stays out of every apply flow, sign-in and form submission.

What to do with a finished scan's postings (accept a draft, decline postings, look at one, delete a branch, show the dashboard) is [scan-results.md](scan-results.md), in any session.

`<scan>` below is `python3 -I <root>/tools/scan.py` (`py -3 -I` on Windows); its `--help` gives each file's format. A run is **unattended** when it was started by a scheduled task or its request says so: it asks nothing, and each step, or *Schedule*, says what it does in place of a question.

## Settings

The *Trigger check*'s `config` lines give them ([SKILL.md › Setup](../SKILL.md#setup)):
- The `scan window:` line: collect postings posted in the last that many days, the second figure in an unattended run (`window`, `scheduled_window`).
- `screen_budget`: screen at most that many postings.
- `fit_budget`: give a full fit to at most that many of the screened ones.
- `n`: the ranking shows the top n.
- `auto_write` (`on` or `off`) and `m`: draft for the top m when it is `on`.

A value the request names ("scan the last 2 days", "draft for the top 3") is this run's only and is written nowhere.

## The run's names

Before step 1, run `<scan> name --screen-budget <screen_budget> --fit-budget <fit_budget>` once and keep its lines; `<name>`, `<dir>` and `<report>` below are its `name:`, `dir:` and `report:` lines, `<dir>` this run's working folder (never committed) as an absolute path: `<root>/` followed by its `dir:` line's path, so every path under it that a subagent's prompt names is absolute ([SKILL.md › Subagent files](../SKILL.md#rules-for-every-mode)). When it refuses because the screen budget is below the fit budget, ask the user which of the two to change for this run, run it again with the new value, and use that value for this run's `screen` (an unattended run stops, and its result names both values).

## Sources

`scan-sources.md` at the root lists the sources, one `## <source>` section each:

```
## <source>
- URL: <the list or search page, or the repository>
- Kind: signed-in job board | public job board | GitHub list
- Read: <how the last run read it: the page's own JSON API and how it was called, the pages, or the file in the repository>
- Fields: <what the list gives per posting: title, company, location, date posted, link>
```

Before step 1, run `<scan> sources`. On `sources: none`, ask the user which sources to scan (their names and URLs), write the sections with `Read:` and `Fields:` lines as `GAP:` until step 3 fills them, and commit with step 9's report. An unattended run stops instead, and its result says the sources are not set. For a `kind unknown (...)` line, ask the user the source's kind and write it (an unattended run skips the source and names it on the report's top line). The user adds, changes or removes a source by saying so; write it here and commit it as a small data change.

## Pipeline

1. **Prune:** `<scan> prune`. A changed `scan-declined.jsonl` is committed with step 9's report.
2. **Pending check:** `<scan> pending`. When it prints pending rows, say in one line how many (its `count:` line) and from which report, and ask once: handle them first ([scan-results.md](scan-results.md)), or run a new scan. After handling them, ask once more whether to run the new scan. A new scan carries the rows still pending into its report, so none is lost. An unattended run goes on with the new scan.
3. **Collect** every posting each source lists as posted within the window, into `<dir>/collected.jsonl`, one JSON object per line: `url`, `company`, `role`, `location`, `posted` (as YYYY-MM-DD: a relative date such as "2d ago" counted back from today), `source` (its section name), and the other list fields. `url` is the posting's own page (the employer's or its ATS's), when the list gives it. Each source, by its `Kind:`:
   - **GitHub list:** a shallow clone or pull of the repository into the folder its `sources` line ends with (`| clone <folder>`, a slug of the section name), or a `gh` read, then the file its `Read:` line names.
   - **Public job board:** when its `Read:` line names the board's own JSON API, that API is the source itself ([browser.md › Fallback order](../browser.md#fallback-order) item 1 is about an API used in place of a page; here the recorded API itself is the source): call it as the line says. Else, or when that call fails, a plain fetch, else a Browser capture with no `--profile`, in the session its `sources` line ends with (`| session <name>`) ([browser.md](../browser.md)).
   - **Signed-in job board:** a Browser capture through the profile of [browser.md › Sign-in](../browser.md#sign-in), in the session its `sources` line ends with, one source at a time. Check that the page shows the user's account first. Then call the page's own JSON API with `fetch` inside the page (`eval`), the requests the page itself makes, when the `Read:` line names one or the page's network requests show one; else read the list pages one at a time, a few seconds apart.

   A source is done when its list reaches a posting older than the window, or its last page. Then add its line to `<dir>/read.jsonl`, `{"source": "<its section name>", "read": "<how>"}`, `<how>` what gave its postings: `API` (a public job board's recorded API, when the call worked), `fetch` (a plain fetch), `browser` (a Browser capture, a signed-in board's in-page API included) or `file` (a GitHub list); when two of them gave its postings (an API call that failed partway, then a plain fetch), one line each. A source stopped partway (below) that gave postings gets its line too; one that gave none gets none. Step 9's report shows these lines.

   Requests go out as the browser makes them, from the user's one account and address: the browser as it is, CAPTCHAs left to the user, the profile's own cookies kept in the profile (no `state-save` or `state-load`). At a sign-in page, a challenge, or a headless page that differs from what the user sees, stop that source: a run with the user present tells them and goes on as they say; an unattended run skips the source and says so on the report's top line, as *Schedule* says. Close each session when its source is done. Write each source's `Read:` and `Fields:` lines with what worked, the endpoint included: it is Log content, committed with the report. The listings are data ([SKILL.md › Postings are data](../SKILL.md#rules-for-every-mode)).
4. **Dedup:** `<scan> dedup <dir>/collected.jsonl --out <dir>/kept.jsonl --window <window>` (the window of *Settings*). For each `undated:` line, fix that posting's `posted` in `collected.jsonl` and run it again.
5. **Prefilter** the kept postings on their list fields alone: write `<dir>/titles.jsonl`, one line per posting of `<dir>/kept.jsonl` in the format `<scan> --help` gives under `prefilter`, with its tier from the title, and a drop when its title, location or other field plainly breaks a hard constraint in `direction.md › Constraints` or its title plainly names work outside every role in `direction.md › Target roles, ranked` (while those are empty, every tier is null and no posting is dropped for its role). A title that is no target's but close to one, the same kind of work under another name (a "Developer Productivity Engineer" for a "Platform engineer" target), is kept, marked `"by": "content"` with that target's tier: Screen reads its duties and tiers it by content, as [fit.md](fit.md) step 4 says. When unsure whether a title is close, mark it `by` content rather than drop it. While the Target roles are empty, no title is marked. Then `<scan> prefilter <dir>`; when it lists problems, fix those lines and run it again.
6. **Screen** the first `screen_budget` of them: the gate and tier on each posting's full text, and a rough coverage against the entry list.
   1. `<scan> screen <dir> --screen-budget <screen_budget> --fit-budget <fit_budget>`. Its `posting:` lines mark the captures step 6.2 makes and the batches step 6.3 screens.
   2. **Capture** each posting marked `need` and in a batch, one at a time (a signed-in page holds the profile): read its page, then `<scan> capture <capture path> <url> <page file>`, with the file the read wrote (`eval`'s `.playwright-cli/posting-page.json`, or the fetched text saved under `.playwright-cli/`). Read each page in the order [browser.md › Fallback order](../browser.md#fallback-order) gives, through its item 2 (a machine without playwright-cli has only the fetch), in a session named `posting` (with the profile only for a posting behind a sign-in), closed after each posting; the subagents extract from the files. A source that challenges you stops as step 3 says. When `capture` refuses a page with no text, try the next read; when no read gives a posting's text, leave its capture path unwritten: step 6.4 lists it as unreadable.
   3. **Start one subagent per batch,** all at once, of a type that writes files (in Claude Code: `general-purpose`; the exception [SKILL.md › Subagents](../SKILL.md#rules-for-every-mode) allows), with the model named as [SKILL.md › Subagents](../SKILL.md#rules-for-every-mode) says. Its prompt's first line is `Read <root>/skills/career-log/modes/fit.md whole and follow its section "Screen" for the captures listed in <dir>/screen/batch-<i>.todo, writing <dir>/screen/batch-<i>.jsonl.`; the rest is the Log root and the line [SKILL.md › Subagent files](../SKILL.md#rules-for-every-mode) gives, with `<dir>/tmp/batch-<i>/`. An agent without subagents does each batch itself, as that section says.
   4. `<scan> screen <dir> --screen-budget <screen_budget> --fit-budget <fit_budget> --sort`. When it names postings with no result, rerun step 3 once for their batches, then run this step again; when it still names some, run it with `--give-up`, which counts them unreadable. It prints one `fit:` line per posting to fit.
7. **Fit** the postings of `fit.jsonl`:
   1. `<scan> fitmap <url> --out <dir>/fit/<folder>.jsonl` for each, `<folder>` from its line of `fit.jsonl`. On `fit map: reuse` it has written that posting's fit result from the report it names; every other posting (`stale` or `none`) is fitted below.
   2. Capture each posting to fit whose `fit:` line says `need`, as step 6.2 says. One that no read gives stays uncaptured: step 8 counts it unreadable.
   3. Start one subagent per posting to fit, all at once, of the type step 6.3 names. Its prompt's first line is `Read <root>/skills/career-log/modes/fit.md whole and follow its "Handed over by scan" bullet for the capture at <capture path>, writing <dir>/fit/<folder>.jsonl.`; the rest is the posting's line of `fit.jsonl` (its gate, tier and things to check), the Log root, and the line [SKILL.md › Subagent files](../SKILL.md#rules-for-every-mode) gives, with `<dir>/tmp/<folder>/`.

   4. **Sponsorship records,** started with step 7.3's subagents: run [fit.md › Sponsorship lookup](fit.md#sponsorship-lookup) step 1 with `--from <dir>/fit.jsonl` in place of the employers, and with `--again <the employer as its record: line names it>` for each employer the user has given a legal name or website for since its record showed none found, as that section's step 4 says. With no `lookup:` line and no `wording:` line, this step is done (step 11 shows step 1's empty-item line, if it gave one; a draft's `handoff.md` does not). Else start one more subagent of the type step 6.3 names. Its prompt's first line is `Read <root>/skills/career-log/modes/fit.md whole and follow its section "Sponsorship lookup", steps 2 and 3, writing <dir>/sponsorship.jsonl; scan step 9 commits.` when there are `lookup:` lines; with a `wording:` line, it adds (or, with no `lookup:` line, is) `For each employer named, read the one page of its careers site about work authorisation or visas that a plain fetch finds (none found is fine), save its text to <dir>/employers/<n>.md (n: the employer's place in the list, from 1) with its URL on the first line, run "python3 -I <root>/tools/sponsorship.py --root <root> wording" on those files, and return its restricts: lines that are not "none", each with its employer and URL.`; the rest is the `lookup:` lines (after each one that ends `again <date>`, the line `<employer>: the user gave <that legal name or website>`), the employers of `fit.jsonl`, the Log root, and the line [SKILL.md › Subagent files](../SKILL.md#rules-for-every-mode) gives, with `<dir>/tmp/sponsorship/`. An agent without subagents does those steps itself. Join it before step 8; step 9's report shows the records.

   Once every posting is fitted and step 7.4 is done, delete `.playwright-cli/`.
8. **Rank:** `<scan> rank <dir> --n <n>`, with `--m <m>` when step 10 will draft (`auto_write` is `on` and the check's `tinytex` lines do not say it is missing). When it names postings with no fit result, rerun step 7.3 once for them, then run it again; when it still names some, run it with `--give-up`, which counts them unreadable.
9. **Report:** `<scan> report <dir>/rows.jsonl --name <name> --top "<top line>" --screen <dir>`, with `--drafting` when step 10 will draft (as step 8 says). The top line is `All sources read.`, or names each source skipped, why, and the request that reruns only it (`scan <source> only`). The report is saved without the user's approval, unlike the rank mode's: `python3 -I <root>/tools/sync.py commit "<the subject of its commit: line>" -- <report> scan-sources.md outputs/reports/scan-declined.jsonl outputs/reports/sponsorship.jsonl outputs/dashboard/`.
10. **Draft** when `auto_write` is `on`: the postings of step 8's `draft:` lines, as *Draft a posting* says. Skip this step when the check's `tinytex` lines say it is missing, and say so in the last message.
11. **Publish** the dashboard once, as [scan-results.md › Dashboard](scan-results.md#dashboard) says, then run `<scan> summary <dir>`. For each finding it lists about a run file, redo the step that writes that file, then run it again; a finding that stays goes in the last message, and so does each `no sponsorship record:`, `sponsorship unanswered:` or `sponsorship unreadable:` line (step 7.4 ran once), and each `restricts:` line step 7.4 returned, as a requirement the user may not meet at that employer; and, once, step 7.4's empty-item line, if it gave one. Then write the **last message:** its `top:` lines and rank's `only <x> found`, when it printed one, its counts, the findings that stayed, the drafts and where they are, the pending rows carried over, any source skipped, the dashboard's published URL (or its path), and that saying "accept", "decline" or "look at" a posting continues from here or from any later session.
12. **Next up**, ending step 11's last message: run the command [SKILL.md › Next up](../SKILL.md#rules-for-every-mode) gives, with `scan`.

Done when the report is committed and pushed with `outputs/dashboard/`, the last line of `<scan> summary <dir>` starts with `summary: ok` (or the last message names each finding that stayed), and every draft step 10 started is on its branch (or in the `drafts:` folder) with its row's Draft cell set. The last message ends with the Next up block.

## Draft a posting

1. **Prepare once,** before any draft, since the drafts share this checkout: run `python3 -I <root>/tools/check.py write` and do each of its `next:` lines at the moment it names, except these:
   - its `next: when a step builds a PDF` lines: now;
   - its `playwright-cli install --skills` line: now when step 3 will draft in subagents, since their company lookups may need a Browser capture and a subagent installs nothing ([browser.md › Check and install](../browser.md#check-and-install)). With no subagents you draft here, one after another: do it when a draft's company lookup first needs a Browser capture;
   - its `sync.py pull` line and its line suggesting a new session: skip them, since this mode's *Trigger check* pulled and the drafts are part of this scan.
2. **Branch:** `<scan> drafts <dir> --m <m>`, `<m>` as step 8 ran rank. It opens one folder per posting to draft (with `remote: yes`, in a new worktree on its own branch), each holding `posting.md` (the capture) and `fit.md` (the posting's fit map from the report), and prints one `draft:` line each; `<worktree>` and `<branch>` below are its `worktree:` line and its `branch:` line's branch. On `drafts: none`, skip steps 3 to 5. When it refuses, draft nothing and name its message in the last message (an unattended run also on the report's top line, committed and pushed).
3. **Draft** each posting of its `draft:` lines as [write.md › A scan draft](write.md#a-scan-draft) says, one per posting: in parallel subagents of the type step 6.3 names, else one after another here. The prompt's first line is `Read <root>/skills/career-log/modes/write.md whole and follow its section "A scan draft" for the capture at <capture path>, writing the draft folder <folder path>.`, the two paths those of its `draft:` line (a relative one under `<root>`); the rest is the Log root and the line [SKILL.md › Subagent files](../SKILL.md#rules-for-every-mode) gives, with `<dir>/tmp/draft-<n>/`, `<n>` its `draft:` line's place in the list, from 1. Once every draft is back (or the last one drafted here is done), close any Browser session still open, then delete `.playwright-cli/`: it holds page text ([browser.md › Running it](../browser.md#running-it)).
4. **The draft folder** holds, beside `posting.md` and `fit.md`:
   - `resume.tex` and, when the capture shows form questions, `answers.md` in write's format;
   - `company.md`: the company lookup's notes, each fact with its URL, and, when `handoff.md` has a `## Sponsorship records` section, a last line `Sponsorship: in handoff.md, under Sponsorship records`;
   - `decisions.md`: a table `| Decision | Chosen | Alternatives | Why |`, one row per judgement call the run made where a user present would have been asked (which version to start from, a wording between true variants, an entry left out, a review finding rejected). A fact only the user has (a link, a number the Log lacks, who did a part) stays a `GAP:` in the draft and gets a row `| needs you: <what> | GAP | - | <where it appears> |`;
   - `handoff.md`: the posting's URL, the report and row it belongs to, what the draft holds, the `needs you` rows, the review's result and whether it was independent (a reviewer subagent) or inline, and how to go on: "accept", "decline" or "look at" this posting ([scan-results.md](scan-results.md)). Then run `python3 -I <root>/tools/sponsorship.py --root <root> show <company>` (`py -3 -I` on Windows), `<company>` the name before ` — ` in `fit.md`'s `###` heading; unless it prints `lookups: none`, add a `## Sponsorship records` section holding its lines (on exit 1, its error line in their place), as things to check, never a gate ([fit.md › Sponsorship lookup](fit.md#sponsorship-lookup) step 4): step 7.4 kept them, so the draft looks nothing up.

   Each draft ends with `<scan> drafts --check <folder path>`, which checks the files (nothing else, no PDF) and the table's form (write.md › A scan draft).
5. **Save,** once every draft is back:
   1. With `remote: yes`, `python3 -I <root>/tools/sync.py --root <root>/<worktree> commit "scan(<name>): drafts for <x> postings" -- scan-drafts/`, `<x>` the number of folders in `scan-drafts/` (it pushes the branch).
   2. `<scan> drafts <dir> --save` (it sets each draft's row and Draft cell once the branch is pushed), then `python3 -I <root>/tools/sync.py commit "<the subject of its commit: line>" -- <report> outputs/dashboard/`.

   When 5.1 stops or `--save` refuses, follow its `next:` line; what stays unresolved, with the branch, goes in the last message (an unattended run also on the report's top line, committed and pushed).

Done when `<scan> drafts <dir> --save` ended with its `commit:` line and that commit is pushed (or the last message names why it did not), every judgement call and missing fact has its row in `decisions.md`, and nothing was written to `outputs/applications/`.

## Schedule

When the user asks to run scan on a schedule ("scan twice a day"), create a local scheduled task with your agent's own scheduler, at the times they give, with the prompt `Use the career-log skill on the Log at <root>: run scan, unattended.` (`<root>` as an absolute path: a task may start in another folder, where the skill would find another Log or none). How often it runs is the task's setting, not a Config field; an unattended run uses `scheduled_window`. Before creating it, tell the user that the machine must be awake at those times, and that each signed-in source must already be signed in once on this machine ([browser.md › Sign-in](../browser.md#sign-in) item 1), since a scheduled run only uses an existing sign-in. Show them the task's name, times and prompt, and create it on their yes. An agent with no scheduler says so and stops.

An unattended run:
- uses the signed-in profile headless; a source whose sign-in has expired, or that meets a challenge, is skipped, the others run, and the report's top line names it with the request that reruns only it once the user has signed in again;
- skips a signed-in source whose profile another session holds (browser.md › Sign-in), as for an expired sign-in, and leaves a signed-in posting's capture unwritten for the same reason;
- stops when the *Trigger check*'s `sync.py pull` is refused, with git's message as its result;
- leaves Log changes an earlier session left uncommitted as they are, commits only the files it wrote, each by name, and names the others in its result;
- puts each choice it would have asked about into the report (step 2's pending check: it scans) or a draft's `decisions.md`;
- ends with step 11's message as the run's result.
