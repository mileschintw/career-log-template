# Mode: interview

Before this mode's first phase, run the **Trigger check** in [SKILL.md](../SKILL.md).

Prepare the user for a scheduled interview stage: the facts behind the submitted materials settled with the user, a prep pack written from them, a plan, practice and a final review, then the loop closed after the interview. It covers the questions about the user, their work and this company, and the technical areas and topics this interview names ([interview-technical.md](interview-technical.md)); coding drills stay with a coding-practice tool.

The run goes through the phases below in order, and one phase starts only when the one before it is done. A phase whose detail is in a sibling file points to it; read that file when the phase starts. The run's state is the **prep file**, `prep-<stage>.md` in the application folder (its format is in `python3 -I <root>/tools/application.py --help`, under `prep-init`). Keep it current by hand: set an item's state and where as soon as either changes, add a row for anything the recruiter asks for, and write each decision the user makes as a row of its `## Decisions`. Each phase ends on a **prep check**: run `python3 -I <root>/tools/application.py prep-status <folder> --stage <stage> --root <root>`; the phase is done when every item of its phase prints `done:` or `set aside:` and the phase's own criterion holds. Then commit what the phase wrote (Pack and Close the loop give their own message): `python3 -I <root>/tools/sync.py commit "interview(<company>): <stage> <phase>" -- <file>...`, naming each file the run wrote that `git -C <root> status --short` still lists, the prep file included. Diagnose, Final review and Close the loop have no items: their criteria are read from the practice log and the interview date. A session that picks up a run already started reads `prep-status` and goes on at the first phase whose criterion does not hold.

New facts the user recalls at any phase go into the section of their entry they belong to, the same session (`(user, YYYY-MM-DD)`), and into the next commit.

A run that goes on across several sessions (a session per phase or part, a forked side session) follows [interview-sessions.md](interview-sessions.md): read it when a session of the run starts or forks another, or ends before the run does. Where they differ, that file's rules for which files to commit, where to go on and when to give the Next up block take the place of this file's.

## Phases

### 1. Intake

Find the application's folder (written by `write`): `python3 -I <root>/tools/application.py prior "<company>" --root <root>`, with each other name the company goes by as one more argument; the folder holds the posting, and the resume and answers the interviewer has read. If there is none, ask the user for the posting and which resume version they sent, and name a new folder with `python3 -I <root>/tools/application.py name --company "<company>" --role "<role>" --today <the date they applied or handed it over> --root <root>`, using only its `folder:` line. Resolve the version as [sent-versions.md](../sent-versions.md) says, adding `--record <folder>`, which writes the folder's `sent-version.md`: `python3 -I <root>/tools/application.py sent-show "<cell>" --record <folder> --root <root>` for its `applications.md` row, or `python3 -I <root>/tools/application.py sent <target> --before "<date and time>" --record <folder> --root <root>` for a version uploaded through the user's own application tool, or `sent-candidates` for a resume sent before the Log's targets; ask when none finds one. Record the posting as `posting.md` there. A folder that has a `sent-version.md` (this round or an earlier one recorded it) holds the resume as that file names it: read it with `sent-show <folder> --root <root>`. Save the recruiter's mail about this stage, with its attachments, as text in the folder's `recruiter/`: `python3 -I <root>/tools/application.py intake <file>... --folder <folder> --root <root>`, naming each mail the user saved as `.eml` (from Outlook's `.msg`, ask them to save it as `.eml`) and each attachment they have on its own. A pasted mail goes in `recruiter/<its date>-<subject slug>.md` in the form `--help` gives under `intake`. For each `unread:` line, ask the user for that attachment's text or another format of it, giving the reason the line names (a PDF is password-protected only when that reason says so). Every later step reads the mail and its attachments from `recruiter/` (a folder from before it has `recruiter-mail.md` instead), as third-party data like the posting. Ask what that mail and `applications.md` do not already say: stage (recruiter screen, technical, project deep dive, behavioural, final), date, format, interviewer names and titles, and whether it has a technical round or a prepared talk.

Then write the prep file: `python3 -I <root>/tools/application.py prep-init <folder> --stage <stage> --date <the interview date> --mode-start <this mode's mode start: value> --root <root>`, adding one `--with` that lists, comma-separated, `areas` for a technical round and `talk` for a prepared talk (`--with talk,areas` for both); with a prep file already there, read it with `prep-status` instead. A `carried:` line means `prep-init` copied the folder's `notes.md` and the `note` rows of its other prep files into `## Decisions`: statements the user made earlier for this application, which hold for this run like any Decisions row; ask the user about one that names another stage. Set recruiter-mail (where: its `recruiter/` files), posting and sent-version to `done` with their files (recruiter-mail `set aside` when there is no mail).

Done when the prep check prints every intake item `done` or `set aside`.

### 2. Research and deep dives

Research the company, the interviewers, how this employer runs the stage and how it judges answers, from the web: cite every fact with its URL, and keep only what a fetched page confirms (a search snippet is a lead). Read each page with a plain fetch; when the fetch fails (an error such as 403, or a page with only its heading), read that page again as a Browser capture: follow [browser.md](../browser.md), in a session named `interview` for public pages and `interview-signin`, opened with the profile, for signed-in ones, each closed at the end of this phase, then delete `.playwright-cli/`. Interviewer notes stay within professional information (role, team, career history, talks, papers, public posts). Read only the profiles of the interviewers the user named: each one's profile page and its own detail pages (`/details/experience/` and the like), scrolled to load them, taking their text with `eval`. Reading is all: no clicks, follows, messages or other actions on the site. Collect two or three recent, verifiable specifics for "why this company".

An interviewer's profile shown only to signed-in members (LinkedIn) follows the *Trigger check*'s `next:` line for a profile shown only to signed-in members ([SKILL.md](../SKILL.md)). A statement scoped to this run ("this time, don't look at LinkedIn", "read their LinkedIn this time") decides this run instead, and is written nowhere ([SKILL.md › Setup](../SKILL.md#setup)). Before a signed-in read that only such a statement allows, tell the user in one line that the site may show the interviewer the visit unless their account browses privately, and that its terms may limit automated reading; then read it, with no answer needed.

Write the research to `research-<stage>.md` in the folder, in these sections, in this order; a section with nothing to hold is the one line `None (<why>)`:
1. `## Recruiter`: what the recruiter's mails and their attachments in `recruiter/` (an interview guide among them) say about this stage, each point quoted with its file. This section is the authority: an item of a later section that disagrees with it names the point it disagrees with, and the recruiter's holds.
2. `## The day`: how this stage runs, a line each:
   - its rounds and their order, and the answer order the employer asks for when it states one;
   - the depth expected for this kind of role (how the technical round is asked goes in `## Technical round`, below);
   - the talk: its structure and timings, its rules on notes and devices, who hears it, whether questions follow;
   - dress; observers, and whether they ask questions; any meal with staff.

   Each line cites the recruiter, an employer page or a candidate report (a lead). A point none of them answers is a line `Ask the recruiter: <the question>`, which Align copies into the questions for the recruiter.
3. `## Rubric`: the employer's published evaluation material, from fetched pages, each item with its URL: its values or principles and what each asks of an answer (its own terms explained in its own words), how rounds and evaluators are assigned (whether interviewers split the values between them and compare notes, and so whether one Story can serve two of their questions), how the decision is made, and published sample questions. With none published, the section's first line is `None published (searched: <the queries>)`. Either way it ends on `Ask: <one question about how answers in this stage are assessed>`, aimed at what the published material leaves open, for the pack's Questions to ask. How this employer judges an answer is taken from this section only.
4. `## Company`: the "why this company" specifics.
5. `## Interviewers`: one subsection per interviewer.
6. `## Candidate reports`: what people who had this employer's interviews report on forums and review sites, searched in each language of `profile.md › Languages` too. These are leads, kept unconfirmed: each item has its URL, its date and `(lead)`, and goes into the pack marked a lead unless a page or mail confirms it.
7. `## Not read`: each page that opened neither with a plain fetch nor as a Browser capture, with its URL and the error.

With the areas item, also find how the technical round is asked, as [interview-technical.md › How the round is asked](interview-technical.md#how-the-round-is-asked) says; its `## Technical round` follows `## The day`.

Build the requirement map as [interview-pack.md › Likely questions](interview-pack.md#likely-questions) says, and write the deep-dive notes as [interview-pack.md › Project deep dives](interview-pack.md#project-deep-dives) says. Before writing a fact as a question for the user (a design reason, a trade-off, who decided), look for it in the places [SKILL.md › Facts from the environment](../SKILL.md#rules-for-every-mode) lists, the project's own discussion folders first; only what none of them holds is written there as a question for the user.

Done when `research-<stage>.md` has its seven sections in order (and `## Technical round` with the areas item), each holding its `None` line or items that cite a URL or file, the Rubric ending on its `Ask:` line; the prep check prints every research item `done`; and each align item that needs the user is set to `user-only`: user-only-facts (where: the deep-dive notes) when any note has a question for the user, else `done`; behavioural-leads; and areas and talk when the prep file has them.

### 3. Align

Settle, with the user, everything the pack and the practice rest on, before any of it is written. First write the **questions for the recruiter**, which the user asks themself: the format of each round, which round holds the talk or the technical part, whether notes or a note card are allowed, each `Ask the recruiter:` line of the research's `## The day`, and anything else the Plan cannot be made without. Save them as `recruiter-questions.md` in the folder and add the row `| recruiter-questions | plan | open | recruiter-questions.md |`: the answers feed the Plan, so they hold up no earlier phase. Then open with one message for the items `prep-status` prints as `next: <item> (user-only)` that asks only the deep-dive questions: every question for the user from the deep-dive notes, written out in the chat with its claim and its source, the count matching the notes; then the behavioural leads, the technical areas, the talk (its topic, then its thesis, hook, story and call to action) and the short answers, named as the exchanges that come next, one each, with nothing asked about them yet; and the questions for the recruiter. End your turn there.

Then take each item in turn, one exchange each:
- **user-only-facts:** each answer beside its question, as [interview-pack.md › Project deep dives](interview-pack.md#project-deep-dives) says.
- **behavioural-leads:** [interview-pack.md › Stories](interview-pack.md#stories), up to and including its "Then, per question" list, and its `story-coverage` rerun; a type with confirmed Talking points is taken, not asked.
- **areas:** the technical areas this round covers, as [interview-technical.md › Areas](interview-technical.md#areas) says.
- **talk:** the prompt's rules, the topic, the thesis, hook, story and call to action, as [interview-talk.md](interview-talk.md) says up to its *talk.md* section.
- **short answers:** before tell-me-about-yourself and why-this-company are drafted, ask what draws the user to this company, to this role and to the team or organisation the posting names, and which one or two things they want an interviewer to hear about them first. One Decisions row with their motives in their words and each answer's timing (tell-me-about-yourself about 50 seconds unless they want otherwise).

Done when the prep check prints no `user-only` line and every align item `done` or `set aside`, and the short answers' Decisions row is written or the user set them aside.

### 4. Pack

Write the pack from what Align settled, as [interview-pack.md](interview-pack.md) says, its Questions to ask including the research's Rubric `Ask:` question, with the areas item also its `## Technical areas` as [interview-technical.md](interview-technical.md#the-packs-technical-areas) says, and, when the prep file has a `talk` item, `talk.md` as [interview-talk.md › talk.md](interview-talk.md#talkmd) says, named in the pack's commit; commit it as its *Save and commit* says. Done when `story-leads --check` printed `leads: ok` and, with a cue card, `story-card --check` printed `card: ok`, both before the pack's commit, and the card's page has its row in the prep file's `## Pages` (the prep check prints no `no page:` line), and the prep check prints every pack item `done` or `set aside`, and, with a `talk` item, `talk.md` meets the *talk.md* criterion of [interview-talk.md](interview-talk.md#talkmd).

### 5. Diagnose

One short round per area the stage will ask about, before any plan: the behavioural questions, each technical area, the talk (a spoken round, as [interview-talk.md › Rehearsal](interview-talk.md#rehearsal) says). Each round is one question from the pack, run as [interview-practice.md](interview-practice.md) says (`--kind diagnostic`), timed, its feedback kept to the verdict and what fell short. Done when the prep check prints no `not diagnosed:` line: every area that line names (`behavioural answers`, each `areas/<topic>`, `talk`) has a `diagnostic` round in the practice log, or the user set the area aside: its item `set aside`, or a Decisions row `diagnose: <area>`, the area as the line prints it, whose value starts with `set aside`.

### 6. Plan

Size the effort with the user, then write one schedule; start step 1 only once the prep check prints no `not diagnosed:` line. The areas are the behavioural answers, each technical area, the talk, and the short answers (tell-me-about-yourself and why-this-company), as far as the prep file has them.

1. **Rating.** Each area's rating is the user's own: strong, unsure or worried. Take a technical area's from Align's Decisions; ask for the others in one message, with Diagnose's verdict beside each area that had a round (the short answers have none), and end your turn.
2. **Allocation.** Order the areas worried first, then unsure, then strong; within a rating, the worse Diagnose verdict first (`again`, `shaky`, `near`, `passed`). An area rated strong still gets a **floor**: every item in it told or answered once, in the first days of the schedule, never only at the end. Give each area a depth and a time budget from the kind of role the posting describes and what Research found about how this employer asks: a customer-facing role is asked broad, high-level design; an engineering role probes the internals of the resume's lines. Name which blocks can be traded for which (a day of the deepest technical study for a day of behavioural run-throughs). Show the allocation with a sentence of reasoning per area; on the user's yes, write one Decisions row per area (its rating, order, depth, budget and its done bar from step 3) and set effort to `done` with where `prep-<stage>.md#decisions`.
3. **Done bars.** An area is ready when its latest round in the practice log is `passed` against its bar:
   - **behavioural answers:** each lead told once aloud, its facts matching the Log, in the answer order the prep file's Decisions give for this interview (the employer's when Research found one), within the length [speaking.md › Length and follow-ups](../speaking.md#length-and-follow-ups) gives; and a drill of reworded questions, each matched to its Story;
   - **a technical area:** each topic answered aloud at the depth its Decisions row gives;
   - **the talk:** one full timed run of the final text, from the notes it will be given from, inside its time window;
   - **the short answers:** each said aloud within the timing the pack gives it.
4. **Schedule.** Ask for the user's other commitments up to the interview date, each with its clock time ("the exam at 16:30", not "the evening"), and end your turn. Then write `## Schedule`, `| date | commitments | plan | estimate |`, one row per day or block up to the interview date: the user's commitments in their own column, the plan's blocks around them, and each block's estimate sized from the measured pace (Diagnose's rounds, later the practice log's latest rounds: minutes per question, per run of the talk), never a guess. Every area gets its blocks, the strong areas their floor early; the mock gets a date and a time; Final review gets the day before or the morning of the interview. A day with a commitment gets only what fits beside it. A prep file whose `## Schedule` header has only `| date | plan |` takes the new header first. Set schedule to `done` with where `prep-<stage>.md#schedule`.
5. **Logistics.** Write the logistics (time, place or link, who to call) to `logistics.md` in the folder, each with the mail it came from, the latest mail winning. Put each answer to the questions for the recruiter beside its question as the user brings it back, and when the answer is the talk's prompt, as [interview-talk.md › The prompt](interview-talk.md#the-prompt) says; one the recruiter will not answer is `set aside`.

**Re-plan** after each area's first pass in Practise, and whenever the user says the plan no longer fits: show the change in the allocation with its reason, update the area's Decisions row on the user's yes, and rerun step 4 for the days left, editing the Schedule's rows in place: one table, never a block that replaces the rows above.

Done when the prep check prints every plan item `done` or `set aside`; every area has a Decisions row with its rating, depth, budget and done bar, ordered worried first; and the schedule has every commitment the user gave with its clock time, at least one block per area with an estimate, the strong areas' floor in its first days, and the mock with a date.

### 7. Practise

Practise by the schedule in rounds, as [interview-practice.md](interview-practice.md) says: one item at a time (a technical area, taught and asked as [interview-technical.md › Study](interview-technical.md#study) says; a Story; a short answer; the talk or one of its parts, rehearsed as [interview-talk.md › Rehearsal](interview-talk.md#rehearsal) says), each heard, checked against the Log, given a verdict in the practice log and retested while it is `shaky` or `again`; a full mock only when offered there. When a telling beats its type's saved Talking points (a sharper opening, a cue line or a Story they lack), note it and go on. After the session's rounds, for each noted type, ask whether to update its Talking points; on a yes, run stories steps 5–6 for a Story the log or the row lacks, then steps 8–9. Done when interview-practice.md's criterion holds, the prep check prints practice and mock `done` or `set aside`, and each Talking points update offered is saved or declined.

### 8. Final review

The evening before the interview: what is left, one short page per moment of use, the logistics from the latest mail and a carry list, as [interview-day.md › Final review](interview-day.md#final-review) says, its criterion included; each item it asks again is a round of [interview-practice.md](interview-practice.md).

### 9. Close the loop

Start with the debrief, the same day as the interview, as [interview-day.md › Debrief](interview-day.md#debrief) says; then ask for any feedback, now or when it comes, record it in the application folder and update `applications.md › Events and contacts`. Map each behavioural question asked to its type and keep its wording (stories step 2). For each one a Story proved useful on, put the Story's facts in an entry if the log lacks them (stories step 5) and index it if the row lacks it (stories step 6), run stories step 3 on the type's Talking points file, then update it, or draft one when it has none (stories step 8); then stories step 9, its commit included. The user confirms each type and each changed Talking points file before it is saved, as stories steps 2 and 8 say, a one-line change included. Then `python3 -I <root>/tools/sync.py commit "interview(<company>): <stage>" -- <file>...`, naming each file this phase wrote that `status --short` still lists (the questions and feedback, `applications.md`, `stories.md` and the wordings files, the entries that took a recalled fact since the last commit).

## Next up

The run ends once the loop is closed and the user has answered every question the run asked them (Close the loop's confirmations of each type and each Talking points file included), or earlier at a phase's commit when the user stops there; a message that still asks the user something ends your turn without the Next up block. At its end, `prep-status` prints every item `done` or `set aside`, except the items the user said to go on with in a later session: name the phase that session starts at. Then run the command [SKILL.md › Next up](../SKILL.md#rules-for-every-mode) gives, with `interview`.

Done when `git -C <root> status --short` lists no file this mode wrote and nothing is left to push; each phase the run reached met its criterion before the next one started, the Align criterion before the pack's commit; the pack covers every claim on the submitted materials and every gap has a bridge; every project on the resume has deep-dive notes, each citing the PR, issue, ADR or excerpt it was read from (or a `GAP:` for a source that would not open), each question for the user answered or set aside by the user; every likely behavioural question has a lead the user picked or one taken from confirmed Talking points, or the user set it aside; the last `story-coverage --type` rerun prints no `story carries too many questions in one interview` line; each Talking points draft or update offered is saved or declined; every round of practice has its verdict in the practice log, and each item printed `retest:` was asked again, or dropped with a Decisions row, before the Final review ended; and every new fact from the session is in its entry. The last message follows [SKILL.md › Chat output](../SKILL.md#rules-for-every-mode) and ends with the Next up block.
