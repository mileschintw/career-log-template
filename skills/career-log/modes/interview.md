# Mode: interview

Before this mode's first step, run the **Trigger check** in [SKILL.md](../SKILL.md).

Prepare the user for a scheduled interview: a prep pack built from what the interviewer read and what the log can defend, then an optional mock interview. Coding drills and generic system-design practice are outside this mode; it covers the questions about the user, their work and this company.

1. **Load the application.** Find its folder (written by `write`): `python3 -I <root>/tools/application.py prior "<company>" --root <root>`, with each other name the company goes by as one more argument; the folder holds the posting, and the resume and answers the interviewer has read. If there is none, ask the user for the posting and which resume version they sent, and name a new folder with `python3 -I <root>/tools/application.py name --company "<company>" --role "<role>" --today <the date they applied or handed it over> --root <root>`, using only its `folder:` line. Resolve the version as [sent-versions.md](../sent-versions.md) says, adding `--record <folder>`, which writes the folder's `sent-version.md`: `python3 -I <root>/tools/application.py sent-show "<cell>" --record <folder> --root <root>` for its `applications.md` row, or `python3 -I <root>/tools/application.py sent <target> --before "<date and time>" --record <folder> --root <root>` for a version uploaded through the user's own application tool; ask when neither finds one. Record the posting as `posting.md` there. A folder that has a `sent-version.md` (this round or an earlier one recorded it) holds the resume as that file names it: read it with `sent-show <folder> --root <root>`. Ask what `applications.md` does not already say: stage (recruiter screen, technical, project deep dive, behavioural, final), date, format, interviewer names and titles.
2. **Research the company and interviewers.** From the web, cite every fact with its URL, and keep only what a fetched page confirms (a search snippet is a lead). Read each page with a plain fetch; when the fetch fails (an error such as 403, or a page with only its heading), read that page again as a Browser capture: follow [browser.md](../browser.md), in a session named `interview` for public pages and `interview-signin`, opened with the profile, for signed-in ones, each closed at the end of this step, then delete `.playwright-cli/`. Interviewer notes stay within professional information (role, team, career history, talks, papers, public posts). Read only the profiles of the interviewers the user named: each one's profile page and its own detail pages (`/details/experience/` and the like), scrolled to load them, taking their text with `eval`. Reading is all: no clicks, follows, messages or other actions on the site. Collect two or three recent, verifiable specifics for "why this company".

   An interviewer's profile shown only to signed-in members (LinkedIn) follows the *Trigger check*'s `next:` line for a profile shown only to signed-in members ([SKILL.md](../SKILL.md)). A statement scoped to this run ("this time, don't look at LinkedIn", "read their LinkedIn this time") decides this run instead, and is written nowhere ([SKILL.md › Setup](../SKILL.md#setup)). Before a signed-in read that only such a statement allows, tell the user in one line that the site may show the interviewer the visit unless their account browses privately, and that its terms may limit automated reading; then read it, with no answer needed.
3. **Build the prep pack.** Sections:
   - **Consistency brief.** Every claim on the submitted resume and answers that the interviewer can probe, each with its entry, its caveat and a one-line deeper answer. Nothing in the room that is not on the paper; everything on the paper defensible in depth. Start from `profile.md › Interview prep list` (skills and claims resting on thin evidence, and known bugs or negative results behind resume claims) and the `## Risks to handle in conversation` section saved with the resume: `python3 -I <root>/tools/application.py risks <folder> --root <root>` prints it, or `risks: none` for a folder saved before that section existed, whose risks you find from its claims.
   - **Likely questions,** in priority order: feedback from earlier rounds, then the posting's requirements the log does not back, then its other requirements, then the stage type. To find them, build a [fit.md › Requirement map](fit.md#requirement-map) on the stated requirements and duties in the folder's `posting.md`, skipping its **Show the map** item and dropping the conditions it takes out, with `--category gap --category "claimed, unbacked"` added to its `fit.py map` command: the rows it prints are the requirements the log does not back; the other requirements are the map file's other rows. A gap gets an honest bridge (acknowledge it, connect the closest real experience, say how the user is closing it), never invented experience.
   - **Stories.** The likely behavioural questions go through the [stories](stories.md) flow: read its intro, then its step 2, mapping them as one interview's pasted list, up to the sentence that starts "Then take the questions one at a time". Here the types are proposed now and confirmed by the user with the leads below, and a predicted question keeps no wording. Run its step 3 for each type whose row links a Talking points file; the type has **confirmed Talking points** when step 3 found the file unchanged or the user reconfirmed it. Then run `python3 -I <root>/tools/entries.py story-leads --type "<question type>"... --root <root>`, one `--type` per question, and do its `next:` line, ending your turn there. A question whose type has confirmed Talking points takes its **lead**, the Story it opens with, from that file's `## Stories` without asking: the Story whose reason best fits this posting, else its first. Show these taken leads in one short list the user may change. For every other question, show its candidates as stories step 4 shows them, with the one you recommend, and ask for its lead. When every type has confirmed Talking points, no lead is asked, but the types and the list are still shown and the turn still ends. Done when the user has answered: every type is confirmed, and every question has a taken lead, a lead the user picked, or was set aside by the user. Write no pack before then. Then, per question, from that answer:
     - A new type the user confirmed: add it with `story-type-add` as stories step 2 says. A type the user changed: run stories step 3 for it if its row links a Talking points file, then rerun `story-leads` for that question and ask again.
     - **Confirmed Talking points** and a lead from its `## Stories`, taken or picked: use the file as it stands.
     - **Otherwise,** unless the question is set aside: run stories steps 5–8 for it and its lead.

     Once every question has its lead or is set aside, rerun `story-coverage --root <root>` with one `--type <question type>=<lead's key>` per question with a lead, and settle each `story carries too many questions in one interview` line with the user as stories step 2 says. Then run stories step 9 for what the flow wrote, its commit included.

     In the pack's `## Stories`, each question is a `### <question>` heading with a `Type: <question type>` line, its Talking points file (or, with none, its lead's entry section), and one `Lead:` line: `Lead: <the Story's key, as story-leads printed it> (user, <the date of their answer>)` for a lead the user picked, `Lead: set aside (user, <that date>)`, or, for a lead taken from confirmed Talking points the user did not change, `Lead: <the Story's key> (<the file>, confirmed <the date on story-leads' talking points: line>)`; facts stay in the entries they link. A stage with no likely behavioural question has the line `None predicted.` there instead.
   - **Project deep dives.** For each project on the resume: the entry's `## How it works`, `## Decisions and trade-offs`, `## Dead ends and mistakes` and `## Likely questions`, condensed to what this stage will probe. Then go below the entry: for each of that project's claims in the resume and answers the interviewer has read, open the sources the entry cites for it (a PR with `gh pr view <its URL> --comments` and `gh pr diff <its URL>`, an issue with `gh issue view <its URL> --comments`, the URL the entry cites, ADRs, excerpts in `sources/`) and note what a follow-up could probe that the entry's own lines leave out: the design detail, how a number was measured and, for a gain, its baseline, what went wrong and how it was found. Each note cites the source it was read from, the PR, issue, ADR or excerpt itself. A claim that rests only on `(user, …)` gets one note saying so; a source that will not open gets `GAP: could not open <source>` for its claim. Write the notes to `deep-dive-<entry file name without .md>.md` in the application folder; a later round reads that file and adds to it. They stay in the application folder: the entry keeps only what [consolidate](consolidate.md) says belongs.
   - **The awkward ones,** answered from the log: why the user left their last role, work authorisation and sponsorship (from `direction.md › Constraints`; when it is empty, list the question as unprepared and say why, [SKILL.md › Setup](../SKILL.md#setup)), the graduation date when `profile.md` gives one, anything an entry's `## Conflicts` makes delicate.
   - **Questions to ask,** four to six, fitted to the stage and the research; drop any the research already answers publicly.
   Save it as `interview-<stage>.md` in the application folder and run `python3 -I <root>/tools/entries.py story-leads --check <the pack> --root <root>` until it prints `leads: ok`. Then present the pack in chat and commit it: `python3 -I <root>/tools/sync.py commit "interview(<company>): <stage> prep" -- <file>...`, so another session or clone has it before the interview, naming each file steps 1–3 wrote that `git -C <root> status --short` still lists (the pack, the `deep-dive-*.md` notes, the files step 1 recorded, and the entries that took a recalled fact under step 5's first rule).
4. **Offer a mock interview.** If accepted, run it in this conversation: a warm-up, then questions from the pack in stage order, one at a time. After each answer give short feedback (what landed, what to sharpen, which story or fact would have served better) in the user's own register from `direction.md`. Judge a behavioural answer against every rule under [speaking.md](../speaking.md)'s *Telling a Story* and *Length and follow-ups*, naming each one it misses by number. When a telling beats its type's saved Talking points (a sharper opening, a cue line or a Story they lack), note it and go on. Finish with a curveball. Then, for each noted type, ask whether to update its Talking points; on a yes, run stories steps 5–6 for a Story the log or the row lacks, then steps 8–9. When the mock ends or is declined, and this mode wrote a file that `status --short` still lists (an entry that took a recalled fact): `python3 -I <root>/tools/sync.py commit "interview(<company>): <stage> prep (mock)" -- <file>...`, naming each. Done when each offer is saved or declined and `status --short` lists no file this mode wrote.
5. **Close the loop.** New facts the user recalls while preparing go into the section of their entry they belong to, the same session (`(user, YYYY-MM-DD)`). After the interview, ask for the questions asked and any feedback: record them in the application folder and update `applications.md › Events and contacts`. Map each behavioural question asked to its type and keep its wording (stories step 2). For each one a Story proved useful on, put the Story's facts in an entry if the log lacks them (stories step 5) and index it if the row lacks it (stories step 6), run stories step 3 on the type's Talking points file, then update it, or draft one when it has none (stories step 8); then stories step 9, its commit included. The user confirms each type and each changed Talking points file before it is saved, as stories steps 2 and 8 say, a one-line change included. Then `python3 -I <root>/tools/sync.py commit "interview(<company>): <stage>" -- <file>...`, naming each file this step wrote that `status --short` still lists (the questions and feedback, `applications.md`, `stories.md` and the wordings files, the entries that took a recalled fact since the last commit).
6. **Next up**, ending the run: after the pack and any mock interview, or after the loop is closed: run the command [SKILL.md › Next up](../SKILL.md#rules-for-every-mode) gives, with `interview`.

Done when `git -C <root> status --short` lists no file this mode wrote and nothing is left to push, the pack covers every claim on the submitted materials, every project on the resume has deep-dive notes, each citing the PR, issue, ADR or excerpt it was read from (or a `GAP:` for a source that would not open), every likely behavioural question has a lead the user picked or one taken from confirmed Talking points, or the user set it aside (`story-leads --check` printed `leads: ok` before the pack's commit), every gap has a bridge, the last `story-coverage --type` rerun prints no `story carries too many questions in one interview` line, each Talking points draft or update offered is saved or declined, and every new fact from the session is in its entry. The last message ends with the Next up block.
