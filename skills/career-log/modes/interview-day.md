# interview: the final review and the debrief

The last two phases' detail for [interview.md](interview.md): *Final review*, the evening before the interview, ending on what the user carries into the room; *Debrief*, the same day after it, before Close the loop. `prep-status` below is `python3 -I <root>/tools/application.py prep-status <folder> --stage <stage> --root <root>`.

## Final review

Start it when `prep-status` prints `days left: 1`, or on the user's word. On the interview day itself (`days left: 0`), ask first whether the interview is over: if it is, go to *Debrief*; if not, do steps 3 and 5 only, and say which steps were skipped. Read every file a step builds from as it stands now: a page built from memory of an earlier session repeats what has since changed.

1. **What is not done.** List, in one message, each item `prep-status` prints on a `retest:` or `not practised:` line, with its latest verdict and weak spots from the practice log. Add the talk, when the prep file has `talk`, unless the practice log has an attempt on `talk` itself (a `talk/<part>` round does not count) dated after the talk file's last change: the text as it now stands has never been run whole. Ask which to do tonight and which to drop, and end your turn; write each answer as a Decisions row `final review: <item>` (`tonight`, or `drop` with the user's reason) until `prep-status` prints no `not reviewed:` line. Run each one the user keeps as one round, the way Diagnose's rounds are written (`practice-add`), the talk as one full timed run. Each one dropped: set its prep row to `set aside` when it is an item.
2. **Pages, one per moment of use.** Ask when the user will look at something tomorrow (on the way, while waiting, before each round) and on what device, and end your turn; the pages are built from that answer. Build the pages below, each readable in two minutes, each from the files named here and nothing recalled; a page may serve two moments.
   - **Behavioural card**, when the stage has behavioural questions: the page of the stage's cue card, `cue-card-<stage>.md`, which holds the finder; build no finder of your own. Run `python3 -I <root>/tools/entries.py story-card --check <the card> --root <root>`. With `card: ok` and the page's row in `## Pages`, use the page as it stands. On a finding (`entry changed since confirmed` among them), settle it and confirm the card again as [stories.md](stories.md) step 9 says, then rebuild the page from the card. With no page yet, build it as stories step 9 says; with no confirmed card, write and confirm it first as [interview-pack.md › Stories](interview-pack.md#stories) says. Either way, the row's `for` takes the moments and device from the user's answer.
   - **Technical card**, when the prep file has `areas`: the practice log's `## Do not say`, at most ten, each with its correction; then the user's own numbers, each with its caveat, from the pack's `## Consistency brief`.
   - **The talk**, when the prep file has `talk`: the file its row names, used as it stands.
   - **One card per interviewer**, only when the interviewers are known: their role and the two or three things from `research-<stage>.md` that bear on this round.

   A fact goes on one page only; another page that needs it names the page that holds it. Write each other card as `day-<card>.md` in the application folder, in the form the user reads on that device. Every page, the talk's file included, gets a row in the prep file's `## Pages` (`| page | built from | link | for |`): the file or files it was built from, its path or the link the user opens it at, and its moments.
3. **Logistics from the latest mail.** Ask whether a newer recruiter mail has come; save a new one into `recruiter/` beside the earlier ones as Intake does (`application.py intake`), its file named by its date. Compare the newest mail with `logistics.md` (with none, with the prep file and the earlier mails): time, place or link, who to ask for, what to bring. Show each difference to the user, the newest mail's value beside the old one and where the old one came from; then update `logistics.md`, the newest mail winning, each line citing its mail. Then answer the questions the day raises, whether or not the user asked them: what to wear, whether an observer or other visitor may join, which round holds the talk, and any the user adds; each from the mails or `research-<stage>.md`, citing it, or marked `unknown` in `logistics.md`.
4. **Questions to ask.** Show the pack's `## Questions to ask`; the user picks two or three, one asking how answers are assessed when the stage allows it. One Decisions row.
5. **The carry list.** Write `carry-<stage>.md` in the folder: one line per page from the prep file's `## Pages`, in the order of use, with its moments, its link and the file it was built from. Then `## Out of date`: each file in the folder that an earlier session built for the user to read and that a carry-list page now replaces (an old card, an earlier cut of the talk), or `none`. A behavioural `day-<card>.md` built before the cue card held the finder is one of them. Show the carry list whole in the phase's last message, as its answer ([SKILL.md › Chat output](../SKILL.md#rules-for-every-mode)).

Then commit: `python3 -I <root>/tools/sync.py commit "interview(<company>): <stage> final review" -- <file>...`, naming each file this phase wrote that `git -C <root> status --short` still lists.

Done when `prep-status` printed no `not reviewed:` line before step 2 began, and each `retest:` and `not practised:` item, and the talk when step 1 added it, has a new verdict in the practice log or a `final review:` row dropping it; every page has its `## Pages` row naming the file it was built from; `logistics.md` cites the newest mail, every difference was shown, and each of step 3's questions is answered or `unknown`; the questions to ask are picked; and `carry-<stage>.md` lists every page in `## Pages`. On the interview day, only step 3's and step 5's parts.

## Debrief

The same day, as soon as the user is back: the wording of a question fades within a day, and the debrief is the run's most useful record. On the interview day `prep-status` prints `days left: 0`, so start it when the user says the interview is over; from the next day it prints `next: close the loop (ask for the questions asked, round by round)` until the debrief file exists. Take one round at a time, in the order they happened, and ask in this order, one exchange each:
1. each question's wording, as close as the user remembers it;
2. for each, the Story or answer given;
3. what went wrong, or what the user would say differently;
4. for the round that held the talk: its length, and the questions asked after it.

Write it as `interview-<stage>-debrief.md` in the application folder: a `## <round>` section per round (its interviewer when known), one `### <question wording>` per question with `Answer:` and `Went wrong:` lines, the user's own words kept; the talk's round adds a `Talk length:` line and a `### Q&A` list of the questions after it. A round the user cannot recall gets the line `Not recalled (user, YYYY-MM-DD)`. Done when every round has its section; then go on to Close the loop, which reads this file and names it in its commit.
