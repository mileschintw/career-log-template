# Mode: log

Before this mode's first step, run the **Trigger check** in [SKILL.md](../SKILL.md).

Capture a milestone in under a minute, without interrupting the user's work. Write and commit directly, then report in one line.

1. **Find the entry.** Match the current work to an entry in `README.md` by project, repo or organisation. When the matched entry has `series: <slug>` in its front matter, it is one part of a split experience: run `python3 -I <root>/tools/entries.py list --root <root> --series <slug> --date <milestone date>`, where the *milestone date* is the milestone's event date (step 2), or today when the evidence gives none, and the milestone goes to the part its `part for` line names; when a `next:` line follows it (the date falls before the first part or between two), do what that line says, and skip the `period` run below. That part is the entry from here on, and its own slug is the `<slug>` of step 4's commit. If no entry fits, create it with `python3 -I <root>/tools/entries.py new <slug> --root <root> --month <YYYY-MM> --status stub --field title=<title> --field period=<period>`, adding a `--field <name>=<value>` for each other front matter field the session can determine (`links` as its comment in `entries/_template.md` says); the tool fills the other fields as `new` in its `--help` says, writes `GAP:` in each section from `One line` to `Likely questions` except the two tables (`Decisions and trade-offs`, `Results and evidence`), writes `status: stub` in the front matter, and rewrites `README.md`'s Entries table. Leave the two tables, `Past phrasings` and `Conflicts` as the tool leaves them, with no `GAP:` line (`Pending` gets step 3's line). A field the user stated, of those *Provenance* in [SKILL.md](../SKILL.md#rules-for-every-mode) names, cites them: add `--field-source <name>="user, YYYY-MM-DD"` for it, dated the day of their turn; every other field keeps its template comment. `--month`, which names the file, is the month the work started, and the period `<YYYY-MM> – ongoing`; when the start is unknown, `--month` is the milestone's month (today's, when the evidence dates nothing) and the period is `GAP – ongoing`. Pass `--field visibility=<value>` only when the user said which it is, or the work is a personal project in a public repo (`public`), with its source as `--field-source visibility="user, YYYY-MM-DD"` or `--field-source visibility=<the repo's URL>`. Then deny the names the entry records, as [commits.md › Names appended to `.export-deny`](../commits.md#names-appended-to-export-deny) says, with the path `new`'s `created:` line prints as the one path. When the milestone date falls outside the entry's `period`, run `python3 -I <root>/tools/entries.py period <entry> --root <root> --cover <milestone date>` (`--ongoing` instead when the work goes on), which also rewrites `README.md`'s Entries table; when it prints a `next:` line, do what it says.
2. **Gather the facts from the current session.** The milestone itself, links (commit SHA, PR, issue, doc), numbers with how they were measured and, for a gain, its baseline (if that is not in context, ask once in one line; with no answer, write `GAP: how measured`), and any decision or feedback that came up. Use what is already in context and cheap lookups (`git log`, `gh pr view`); skip anything that needs a long investigation. When the user calls the skill partway through the work, the day of the call is not the day anything happened: give a date to an event (a merge, a release, a run) only when evidence shows it (`gh pr view`, the commit date), and never ask the user for one. A user's turn in this session saying the event happened that day ("it just merged", "merged this morning") is such evidence when no lookup gives a date: it dates the event to that turn's day, cited `(user, YYYY-MM-DD)`. A turn that dates it any other way ("yesterday", "last week") is not: the event stays undated until a lookup dates it.
3. **Add to `## Pending`:** `python3 -I <root>/tools/entries.py pending-add <entry> --root <root> -- "<line>"`, one line per milestone, in the record language, at most two sentences plus links:
   `<what happened, with any event date the evidence gives inside the sentence>. <links>`
   Start the text with what happened: the tool writes the leading date itself (today, the day recorded), so a number in the line holds as of that day. When it prints `renamed:`, the entry had an old `## Log` section: apply *Old sections* in `python3 -I <root>/tools/entries.py --help` to the lines that were under it. Detail a link holds (paths, a script's output, the commit a test ran on) stays at the link. When the user said something worth keeping (why a decision went one way, a judgement, feedback), paraphrase it in the line and excerpt the turn ([excerpts.md](../excerpts.md)); the line cites `(user, YYYY-MM-DD; <key> U<k>)`. Leave the other sections alone: placing pending lines in them is consolidate's job.
4. **Commit and push:** `python3 -I <root>/tools/sync.py commit "log(<slug>): <milestone>" -- <file>...`, naming the entry, `README.md` when step 1 printed `readme written:`, and each excerpt step 3 wrote, where `<slug>` is the entry's file name without the leading `<YYYY-MM>-` and the `.md`, as `tools/entries.py list` prints it (`entries/2031-04-widget.md` commits as `log(widget): ...`).
5. **Report** to the user in one line: which entry, what was logged. Run `python3 -I <root>/tools/entries.py state <entry> --root <root>`; when it prints a `suggest consolidate:` line, add one sentence suggesting consolidate, with that line's reasons. A milestone is a Story when its pending line names an action or decision of the user's that answers a question type of the Story index (the first table of `stories.md`). When it is one, run `python3 -I <root>/tools/entries.py story-candidates "<best-fit type>" --root <root>`; unless it prints an `indexed:` line whose key is this entry's `entries/<file>.md#pending`, add one sentence offering to index it under that type; name any other type it answers as an alternative. With no fitting type, or no Story index, there is no offer.
6. **Index the Story,** on the user's yes to that offer: `python3 -I <root>/tools/entries.py story-add "<the type the user picked>" entries/<file>.md#pending --summary "<one-line summary>" --root <root>`; on `already linked:`, tell the user so. Then `python3 -I <root>/tools/sync.py commit "log(<slug>): index pending Story under <question type>" -- stories.md`.

Done when the pending line, and its excerpt if it cites one, is pushed, and the user has the one-line report, with the Story offer when step 5 makes it; on a yes to it, the index line is pushed too.
