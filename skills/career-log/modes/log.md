# Mode: log

Before this mode's first step, run the **Start check** in [SKILL.md](../SKILL.md), once per session.

Capture a milestone in under a minute, without interrupting the user's work. Write and commit directly, then report in one line.

1. **Find the entry.** Match the current work to an entry in `README.md` by project, repo or organisation. When the matched entry has `series: <slug>` in its front matter, it is one part of a split experience: run `python3 -I <root>/tools/entries.py list <root> --series <slug>`, and the milestone goes to the finished part whose period holds its event date (step 2) when it has one; otherwise to the part the list marks `(ongoing)`, or, with none, the part whose period ends last. That part is the entry from here on, and its own slug is the `<slug>` of step 4's commit. If no entry fits, create `entries/<YYYY-MM>-<slug>.md` from `entries/_template.md`: fill the front matter fields the session can determine and write `GAP: <what is missing>` in every other one (`my_role: GAP: role title`), except that `links` holds what its comment in the template says (`[]` when the session knows none), an empty `tags` stays `[]`, `series` stays empty, and an unknown start month is written `GAP – ongoing` (or `GAP – YYYY-MM`), as [import](import.md) step 4 writes it. `visibility` stays `GAP` unless the user said which it is, or the work is a personal project in a public repo (`public`); a value other than `GAP` replaces the template's comment with its source (`visibility: nda  # (user, YYYY-MM-DD)`). Leave every other section as `GAP:`, add a row to `README.md` with status `stub`, and once the entry is written, deny the names it records, as *Names appended to `.export-deny`* in [SKILL.md › Commits](../SKILL.md#rules-for-every-mode) says, with `<root>/entries/<YYYY-MM>-<slug>.md` as the one path. If the milestone falls outside the entry's `period`, extend it (or set it to `ongoing`) and update its `README.md` row; in a series, extend only the end of the part whose period ends last, since the parts' periods must not overlap.
2. **Gather the facts from the current session.** The milestone itself, links (commit SHA, PR, issue, doc), numbers with how they were measured (if that is not in context, ask once in one line; with no answer, write `GAP: how measured`), and any decision or feedback that came up. Use what is already in context and cheap lookups (`git log`, `gh pr view`); skip anything that needs a long investigation. When the user calls the skill partway through the work, the day of the call is not the day anything happened: give a date to an event (a merge, a release, a run) only when evidence shows it (`gh pr view`, the commit date), and never ask the user for one. A user's turn in this session saying the event happened that day ("it just merged", "merged this morning") is such evidence when no lookup gives a date: it dates the event to that turn's day, cited `(user, YYYY-MM-DD)`. A turn that dates it any other way ("yesterday", "last week") is not: the event stays undated until a lookup dates it.
3. **Add to `## Pending`** (if the entry still has `## Log`, rename it first: SKILL.md › Entry sections renamed). One line per milestone, newest last, in the record language, at most two sentences plus links:
   `- YYYY-MM-DD: <what happened, with any event date the evidence gives>. <links>`
   The leading date is the day it was recorded: a number recorded then holds as of that day. Detail a link holds (paths, a script's output, the commit a test ran on) stays at the link. When the user said something worth keeping (why a decision went one way, a judgement, feedback), paraphrase it in the line and excerpt the turn ([excerpts.md](../excerpts.md)); the line cites `(user, YYYY-MM-DD; <key> U<k>)`. Update the frontmatter's `last_updated`. Leave the other sections alone: placing pending lines in them is consolidate's job.
4. **Commit and push** in the career-log repo, with any excerpt from step 3 in the same commit, each file added by name: `log(<slug>): <milestone>`, where `<slug>` is the entry's file name without the leading `<YYYY-MM>-` and the `.md`, as `tools/entries.py list` prints it (`entries/2031-04-widget.md` commits as `log(widget): ...`).
5. **Report** to the user in one line: which entry, what was logged. When the entry now has five or more pending lines, its oldest pending line is over a month old, or its body is mostly `GAP`, add one sentence suggesting consolidate, saying which of these holds. A milestone is a Story when its pending line names an action or decision of the user's that answers a question type of the Story index (the first table of `stories.md`). When it is one, and the best-fit type's row does not link this entry's `#pending` yet, add one sentence offering to index it under that type; name any other type it answers as an alternative. With no fitting type, or no Story index, there is no offer.
6. **Index the Story,** on the user's yes to that offer: add `*(pending)* [<entry title> › Pending](entries/<file>.md#pending) — <one-line summary>` to the Stories cell of the row the user picked, after a `; ` when the cell holds other items; when that row already links this entry's `#pending`, tell the user so instead. This is the Story index format of the docstring at the top of `tools/entries.py` (*Stories*): a `|` or `]` in the entry title is written `\|` or `\]`, and the summary holds no `|`, `; [` or `; *(`. Commit and push `stories.md` alone: `log(<slug>): index pending Story under <question type>`.

Done when the pending line, and its excerpt if it cites one, is pushed, and the user has the one-line report, with the Story offer when step 5 makes it; on a yes to it, the index line is pushed too.
