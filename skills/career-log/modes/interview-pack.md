# interview: the prep pack

The prep pack of [interview.md](interview.md): what the interviewer can probe, and what the log answers it with. Three phases use this file. Research builds *Likely questions*' requirement map and writes *Project deep dives*' notes with their questions for the user; Align takes the answers to those questions and the leads under *Stories*; Pack writes every section from what Align settled, each as a `##` section of the pack under the same heading, and runs *Save and commit*.

## Consistency brief

Every claim on the submitted resume and answers that the interviewer can probe, each with its entry, its caveat and a one-line deeper answer. Nothing in the room that is not on the paper; everything on the paper defensible in depth. Start from `profile.md › Interview prep list` (skills and claims resting on thin evidence, and known bugs or negative results behind resume claims) and the `## Risks to handle in conversation` section saved with the resume: `python3 -I <root>/tools/application.py risks <folder> --root <root>` prints it, or `risks: none` for a folder saved before that section existed, whose risks you find from its claims. When the folder's `sent-version.md` names several candidate versions (the user does not know which one the employer read), `risks` then prints each line that is not in every version, on a `line (version …):` or `line (versions …):` line naming the versions that hold it: the brief covers each of those claims too, marked with its versions, so the user can answer for whichever version the interviewer read. For a version printed `not text:` (an imported PDF), read its claims as that line says. A claim a deep-dive question was about takes the user's answer from Align, as they gave it: the claim weaker, or a seeming contradiction gone.

## Likely questions

In priority order: feedback from earlier rounds, then the posting's requirements the log does not back, then its other requirements, then the stage type. To find them, build a [fit.md › Requirement map](fit.md#requirement-map) on the stated requirements and duties in the folder's `posting.md`, skipping its **Show the map** item and dropping the conditions it takes out, with `--category gap --category "claimed, unbacked"` added to its `fit.py map` command: the rows it prints are the requirements the log does not back; the other requirements are the map file's other rows. A gap gets an honest bridge (acknowledge it, connect the closest real experience, say how the user is closing it), never invented experience.

## Stories

The likely behavioural questions go through the [stories](stories.md) flow: read its intro, then its step 2, mapping them as one interview's pasted list, up to the sentence that starts "Then take the questions one at a time": the mapping, the merge plan and its `## Decisions` rows. For the plan's core proposal, run `story-coverage --root <root>` once here and read its `core stories outside 3–5:` line as stories step 1 does. Here the types are proposed now and confirmed by the user with the leads below, and a predicted question keeps no wording. Run its step 3 for each type whose row links a Talking points file; the type has **confirmed Talking points** when step 3 found the file unchanged or the user reconfirmed it. Then run `python3 -I <root>/tools/entries.py story-leads --brief --type "<question type>"... --root <root>`, one `--type` per question, and do its `next:` line (it runs the full form, without `--brief`, for the questions whose lead is asked), ending your turn there. A question whose type has confirmed Talking points takes its **lead**, the Story it opens with, from that file's `## Stories` without asking: the Story whose reason best fits this posting, else its first. Show the questions as stories step 2's merge plan, its rows, switch rule, common types and core proposal: a taken lead fills its row, for the user to change; every other row gets the lead you recommend from its candidates (shown as stories step 4's *Candidates* part shows them), and the user picks its lead. When every type has confirmed Talking points, no lead is asked, but the types and the plan are still shown and the turn still ends. Done when the user has answered: every type is confirmed, and every question has a taken lead, a lead the user picked, or was set aside by the user. Write no pack before then. Then, per question, from that answer:
- A new type the user confirmed: add it with `story-type-add` as stories step 2 says. A type the user changed: run stories step 3 for it if its row links a Talking points file, then rerun `story-leads` for that question and ask again.
- **Confirmed Talking points** and a lead from its `## Stories`, taken or picked: use the file as it stands.
- **Otherwise,** unless the question is set aside: in the list's order, show stories step 4's brief for it with the lead already picked in place of its Ask (the user may still change it), then run steps 5–8 for it and its lead.

Once every question has its lead or is set aside, rerun `story-coverage --root <root>` with one `--type <question type>=<lead's key>` per question with a lead (and `--interviewers` as stories step 2 says), and settle each `story carries too many questions in one interview` line with the user as stories step 2 says. Write the plan into the prep file's `## Decisions` as stories step 2 says. Write the stage's cue card as stories step 8 says under *The cue card*: a lead taken from confirmed Talking points gets its row here too, from the entry sections that file links, and the finder lives in the card. Then run stories step 9 for what the flow wrote, the card's confirmation and page and the commit included.

In the pack's `## Stories`, a first line links the card, `Cue card: [cue-card-<stage>.md](cue-card-<stage>.md)`; then each question is a `### <question>` heading with a `Type: <question type>` line, its Talking points file (or, with none, its lead's entry section), and one `Lead:` line, in the form the `next:` line of `story-leads` gives for its kind; facts stay in the entries they link. A stage with no likely behavioural question has the line `None predicted.` there instead.

## Project deep dives

For each project on the resume: the entry's `## How it works`, `## Decisions and trade-offs`, `## Dead ends and mistakes` and `## Likely questions`, condensed to what this stage will probe. Then go below the entry: for each of that project's claims in the resume and answers the interviewer has read, open the sources the entry cites for it (a PR with `gh pr view <its URL> --comments` and `gh pr diff <its URL>`, an issue with `gh issue view <its URL> --comments`, the URL the entry cites, ADRs, excerpts in `sources/`) and note what a follow-up could probe that the entry's own lines leave out: the design detail, how a number was measured and, for a gain, its baseline, what went wrong and how it was found. Each note cites the source it was read from, the PR, issue, ADR or excerpt itself. A claim that rests only on `(user, …)` gets one note saying so; a source that will not open gets `GAP: could not open <source>` for its claim. Write the notes to `deep-dive-<entry file name without .md>.md` in the application folder; a later round reads that file and adds to it. They stay in the application folder: the entry keeps only what [consolidate](consolidate.md) says belongs.

A fact only the user can give is a **question for the user**: a source that seems to contradict a claim, a number with no stated measurement or baseline, which part of a gain came from which change, what a demo really ran, a design reason no source states. Write it under the note file's `## Questions for the user` heading, one line each, with the claim, the source and what it says ("the poster says X, dated before the result; was the result ready by then?"), never as a conclusion about the claim. Align asks them; each answer goes beside its question, `(user, YYYY-MM-DD)`, and a fact the entry lacks goes into its entry section too.

## Tell me about yourself

The background the interviewer digs into, not the stories themselves. A `Timing:` line (the one Align recorded, about 50 seconds by default), then three to five cue lines, each naming the entry or `profile.md` line it comes from: where the user is now; the one or two achievements the resume leads with, each one clause with no number, a door for a follow-up; and why this role next, from the motive the user gave in Align. Cue lines, not a script: the user says them in their own words.

## Why this company

Why this company, then why this role (and the team or organisation, when the posting names one), each a `Timing:` line and two or three cue lines. Each opens from the motive the user gave in Align, in their words, and ties it to one of Research's specifics (with its URL), an entry, or a line of `direction.md`: why here and this role, not the field in general.

## The awkward ones

Answered from the log: why the user left their last role, work authorisation and sponsorship (from `direction.md › Constraints`; when it is empty, list the question as unprepared and say why, [SKILL.md › Setup](../SKILL.md#setup)), the graduation date when `profile.md` gives one, anything an entry's `## Conflicts` makes delicate.

## Questions to ask

Four to six, fitted to the stage and the research; drop any the research already answers publicly.

## Save and commit

Save the pack as `interview-<stage>.md` in the application folder and run `python3 -I <root>/tools/entries.py story-leads --check <the pack> --root <root>` until it prints `leads: ok`; with a cue card, also run `python3 -I <root>/tools/entries.py story-card --check <folder>/cue-card-<stage>.md --root <root>` until it prints `card: ok` (an unconfirmed card fails it: take it through stories step 9's confirmation first). Set the prep file's pack items to `done`, each with its section as where: tell-me-about-yourself `interview-<stage>.md#tell-me-about-yourself`, why-this-company `interview-<stage>.md#why-this-company`, awkward-questions `interview-<stage>.md#the-awkward-ones`. Then present the pack in chat as [SKILL.md › Chat output](../SKILL.md#rules-for-every-mode) says (what this stage will probe hardest and the pack's path, with hooks such as one project's deep dive or a practice round) and commit it: `python3 -I <root>/tools/sync.py commit "interview(<company>): <stage> prep" -- <file>...`, naming each file the run wrote that `git -C <root> status --short` still lists (the pack, the prep file, the entries that took a recalled fact).
