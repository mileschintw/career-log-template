# Mode: stories

Before this mode's first step, run the **Trigger check** in [SKILL.md](../SKILL.md).

Prepare what the user says aloud to behavioural questions, one question at a time, with or without an application. Read [speaking.md](../speaking.md) first: the Talking points and any feedback on a telling follow it.

The mechanical steps are subcommands of `python3 -I <root>/tools/entries.py`: `story-coverage`, `story-candidates`, `story-stale`, `story-wordings`, `story-wording-add`, `story-type-add`, `story-add`, `story-core` and `story-confirm`. `python3 -I <root>/tools/entries.py --help` prints the formats of the Story index, a Talking points file and a wordings file, and what each output line means, under *Stories*. The subcommands write `stories.md` and the wordings files, except a fix step 9 names; you write a Talking points file as `--help` gives it, all but its `confirmed:` line.

1. **Coverage report.** Run `story-coverage --root <root>` and show the user its findings in a few lines. When it prints `core stories outside 3–5:`, propose entries to mark core when there are too few (speaking.md rule 9's high impact, complexity and personal involvement, judged from the entries, with `types per entry:` showing which already serve several types), or which to unmark when there are too many. On the user's yes, run `story-core <entry> on|off --root <root>` for each; an entry it prints `not indexed:` for gets core when its Story is indexed: in step 6, or with `story-add ... --marker core` now under a type the user confirms. Done when the findings are shown and the user has answered the proposal or passed; then go on to step 2 whatever they decided.
2. **Map each question to a type.** Run `story-wordings --root <root>` and propose the index type that covers the question, from the type names and the wordings it lists, and relay any `wordings type not in stories.md` or `wordings file with no type` line; the user confirms. A question no type covers gets a proposed new type, confirmed by the user and added with `story-type-add "<question type>" --root <root>` (on `FAIL: stories.md has this question type already: <type>`, use that type; on another `FAIL:`, propose another name). Once the type is confirmed and its row is in `stories.md`, keep the wording of a question the user brought (asked, pasted, or recalled from an interview), Talking points or not: `story-wording-add --root <root> "<question type>" "<the question, word for word>"`. Only a question the user brought keeps a wording; one you predicted is not one. Done when the type is confirmed and, for a question the user brought, the tool printed `added:` or `already kept:`.
   - **A pasted list from one interview:** map every question first, then run `story-coverage --root <root>` with one `--type <question type>` per question, and relay any `story carries too many questions in one interview` line with a proposal of which questions should lead with another Story; rerun with `--type <question type>=<key>` for the ones the user moves. Then take the questions one at a time, steps 3–8 each.
   - **A story to keep, with no question** ("this is a good story, keep it"): propose the types it answers; for each type the user confirms, run steps 5–7, and step 8 only when the user wants Talking points.
3. **Staleness check.** When the type's row links a Talking points file, run `story-stale <the file the row links> --root <root>` before using it. On exit 1, show each change (`--help`, under `story-stale`, says how to diff it) and ask the user whether the Talking points still hold: reconfirmed as they are, run `story-confirm <the file> --root <root>`; otherwise revise them in step 8.
4. **Candidates.** Run `story-candidates "<question type>" --root <root>` and show, in its order, the Stories on its `talking points <n>:` lines (marked "confirmed") and `indexed:` lines, then the `not yet indexed:` and `pending:` lines whose facts could answer this question, marked "not yet indexed". Give each a one-line summary and its entry. Ask: use one of these, tell another story, or talk through which to use. Done when the user has picked a Story, told another, or set the question aside.
5. **A Story the log lacks.** When the user tells a story no entry holds, its facts go into an entry: the existing entry for that experience, or a new one created as [log](log.md) step 1 creates one. Each fact goes in its section the same session, cited as [SKILL.md › Provenance](../SKILL.md#rules-for-every-mode) says for the user's words, with an excerpt of the turn ([excerpts.md](../excerpts.md)). Talking points only point at facts; a fact lives in its entry. An answer that contradicts the entry follows [SKILL.md › Current truth only](../SKILL.md#rules-for-every-mode).
6. **Index the chosen Story.** Run `story-add "<question type>" entries/<file>.md#<section anchor> --summary "<one line>" --root <root>`, with the anchor of the section that holds its facts: its heading lowercased, spaces as `-`, and every character other than a letter, digit, `-` or `_` dropped (`## Decisions and trade-offs` is `#decisions-and-trade-offs`); `#pending` when its facts sit only in `## Pending`; and `--marker core` when the user said yes in step 1 to marking this experience core and `story-core` printed `not indexed:` for it. Done when it printed `added:` or `already linked:`.
7. **Deepen.** Grill the user on the chosen Story, one question at a time, each with your own guess from the entry for them to confirm or correct. Ask only what the entry lacks for the telling and its first follow-ups: the user's own actions and attribution, scope (people, teams), the trade-offs weighed, how a result was measured, what went wrong, the lesson. Each answer goes into its entry section the same session, with its source as step 5 says; a likely follow-up and its answer go in the entry's `## Likely questions`. Done when the entry holds each of those, as a fact or as a `GAP:` the user could not fill.
8. **Talking points.** Draft the type's file with the sections `--help` gives for a Talking points file, in its order (step 9's run checks the order and the cue-line count). What goes in them:
   - `order:` `result-first` for a senior or complex Story (speaking.md rule 5), else `chronological`: you propose, the user decides.
   - `## Stories`: two or three, in order of preference, each with when to lead with it; when a posting is known, recommend which to lead with for it. One file per type: an angle is a reason in this list, never a second file.
   - `## Opening`: the only full sentence, a headline that may lead with the result; a number in it links its entry section.
   - `## Cue lines`, in telling order: context (two lines at most), then the actions, most of the lines, each one thing the user did, said with "I", then the result, then the lesson. Each line is a few words and a link to the entry section that holds its facts, with no numbers, results or technical detail copied in. About 7 lines at most; detail beyond that moves to `## Likely questions`.
   - `## Follow-ups`: links to each chosen Story's `## Likely questions`.

   Show the draft and save it only when the user confirms it: write the file at the path `story-candidates` named on its `talking points:` line, then run `story-confirm <that path> --type "<question type>" --root <root>`, which writes `confirmed:` and links the row's type to the file. On `type differs:`, write the row's type in the file's `type:` line and run it again; relay `row links another file:` to the user, who picks which file the row keeps. Declined, no Talking points file is written; what steps 2, 5 and 7 wrote stays.
9. **Close.** Run `story-coverage --talking-points --root <root>`. Fix these findings for the rows and files this run wrote: `index names a missing entry`, and the six about Talking points files (`row links a missing talking points file`, `talking points file no row links`, `talking points type differs from its row`, `talking points with no readable confirmed date`, `talking points sections out of order`, `talking points over 7 cue lines`; a fix to a saved file goes back to the user as step 8 says). Report the others. Then `python3 -I <root>/tools/sync.py commit "stories(<slug>): <what changed>" -- <file>...`, naming each file this run wrote, the wordings files step 2 wrote included, with the slugs of a pasted list comma-separated.
10. **Next up**, after step 9's commit: run the command [SKILL.md › Next up](../SKILL.md#rules-for-every-mode) gives, with `stories`.

Done when every question in the request has a confirmed type and a chosen Story (or the user set it aside, and the report says so), every fact the user gave is in its entry with its source, each Talking points draft is saved or declined by the user, and the last `story-coverage` prints none of step 9's findings for what this run wrote. The last message ends with the Next up block.
