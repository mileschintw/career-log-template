# Mode: stories

Before this mode's first step, run the **Start check** in [SKILL.md](../SKILL.md), once per session.

Prepare what the user says aloud to behavioural questions, one question at a time, with or without an application. Read [speaking.md](../speaking.md) first: the Talking points and any feedback on a telling follow it.

The mechanical steps are subcommands of `python3 -I <root>/tools/entries.py`: `story-coverage`, `story-candidates`, `story-stale`, `story-wordings` and `story-wording-add`. `python3 -I <root>/tools/entries.py --help` prints the formats of the Story index, a Talking points file and a wordings file, and what each output line means, under *Stories*. Write the first two exactly as it gives them; a wordings file is written by `story-wording-add` alone. Where a step sets `confirmed:` to now, write the current local date and time, `YYYY-MM-DD HH:MM`, so that a reconfirm on the same day changes the line `story-stale` looks for.

1. **Coverage report.** Run `story-coverage <root>` and show the user its findings in a few lines. When the core count (`core stories:`) is below 3, propose entries to mark core: speaking.md rule 9's high impact, complexity and personal involvement, judged from the entries, with `types per entry:` showing which already serve several types; above 5, propose which to unmark. On the user's yes, add `core` to the markers of one item of that experience in the index, or take it from every item of it (every part of a series). Done when the findings are shown and the user has answered the proposal or passed; then go on to step 2 whatever they decided.
2. **Map each question to a type.** Run `story-wordings <root>` and propose the index type that covers the question, from the type names and the wordings it lists, and relay any `wordings type not in stories.md` or `wordings file with no type` line; the user confirms. A question no type covers gets a proposed new type (no `|` or `;` in it), confirmed by the user and added as a row with an empty Stories cell. Once the type is confirmed and its row is written in `stories.md`, keep the wording of a question the user brought (asked, pasted, or recalled from an interview), Talking points or not: `story-wording-add "<question type>" "<the question, word for word>" <root>`. Only a question the user brought keeps a wording; one you predicted is not one. Done when the type is confirmed and, for a question the user brought, the tool printed `added:` or `already kept:`.
   - **A pasted list from one interview:** map every question first, then run `story-coverage <root>` with one `--type <question type>` per question, and relay any `story carries too many questions in one interview` line with a proposal of which questions should lead with another Story; rerun with `--type <question type>=<key>` for the ones the user moves. Then take the questions one at a time, steps 3–8 each.
   - **A story to keep, with no question** ("this is a good story, keep it"): propose the types it answers; for each type the user confirms, run steps 5–7, and step 8 only when the user wants Talking points.
3. **Staleness check.** When the type's row links a Talking points file, run `story-stale <the file the row links> <root>` before using it. On exit 1, show each change (`--help`, under `story-stale`, says how to diff it) and ask the user whether the Talking points still hold: reconfirmed as they are, set `confirmed:` to now; otherwise revise them in step 8.
4. **Candidates.** Run `story-candidates "<question type>" <root>` and show, in its order: the Talking points file's Stories (confirmed), the Stories the row indexes, then the entries and `## Pending` lines it lists whose facts could answer this question, each of these marked "not yet indexed". Give each a one-line summary and its entry. Ask: use one of these, tell another story, or talk through which to use. Done when the user has picked a Story, told another, or set the question aside.
5. **A Story the log lacks.** When the user tells a story no entry holds, its facts go into an entry: the existing entry for that experience, or a new one created as [log](log.md) step 1 creates one. Each fact goes in its section the same session, cited as [SKILL.md › Provenance](../SKILL.md#rules-for-every-mode) says for the user's words, with an excerpt of the turn ([excerpts.md](../excerpts.md)). Talking points only point at facts; a fact lives in its entry. An answer that contradicts the entry follows [SKILL.md › Current truth only](../SKILL.md#rules-for-every-mode).
6. **Index the chosen Story.** A chosen Story the row does not list yet is added to it, labelled `<entry title> › <section>` and linking that section; one whose facts sit only in `## Pending` links `#pending` and carries the `pending` marker.
7. **Deepen.** Grill the user on the chosen Story, one question at a time, each with your own guess from the entry for them to confirm or correct. Ask only what the entry lacks for the telling and its first follow-ups: the user's own actions and attribution, scope (people, teams), the trade-offs weighed, how a result was measured, what went wrong, the lesson. Each answer goes into its entry section the same session, with its source as step 5 says; a likely follow-up and its answer go in the entry's `## Likely questions`. Done when the entry holds each of those, as a fact or as a `GAP:` the user could not fill.
8. **Talking points.** Draft the type's file with the sections `--help` gives for a Talking points file, in its order. What goes in them:
   - `order:` `result-first` for a senior or complex Story (speaking.md rule 5), else `chronological`: you propose, the user decides.
   - `## Stories`: two or three, in order of preference, each with when to lead with it; when a posting is known, recommend which to lead with for it. One file per type: an angle is a reason in this list, never a second file.
   - `## Opening`: the only full sentence, a headline that may lead with the result; a number in it links its entry section.
   - `## Cue lines`, in telling order: context (two lines at most), then the actions, most of the lines, each one thing the user did, said with "I", then the result, then the lesson. Each line is a few words and a link to the entry section that holds its facts, with no numbers, results or technical detail copied in. About 7 lines at most; detail beyond that moves to `## Likely questions`.
   - `## Follow-ups`: links to each chosen Story's `## Likely questions`.

   Show the draft and save it only when the user confirms it: write the file at the path `story-candidates` named on its `talking points:` line, with `confirmed:` now, and link the row's type to that path. Declined, no Talking points file is written; what steps 2, 5 and 7 wrote stays.
9. **Close.** Run `story-coverage <root>` again. Fix these findings for the rows and files this run wrote: `index names a missing entry`, and the four about Talking points files (`row links a missing talking points file`, `talking points file no row links`, `talking points type differs from its row`, `talking points with no readable confirmed date`). Report the others. Commit and push, the wordings files step 2 wrote included, as [SKILL.md › Commits](../SKILL.md#rules-for-every-mode) says, with the message `stories(<slug>): <what changed>`, the slugs of a pasted list comma-separated.

Done when every question in the request has a confirmed type and a chosen Story (or the user set it aside, and the report says so), every fact the user gave is in its entry with its source, each Talking points draft is saved or declined by the user, and the last `story-coverage` prints none of step 9's findings for what this run wrote.
