# Mode: stories

Before this mode's first step, run the **Trigger check** in [SKILL.md](../SKILL.md).

Prepare what the user says aloud to behavioural questions, one question at a time, with or without an application. Read [speaking.md](../speaking.md) first: the Talking points and any feedback on a telling follow it.

The mechanical steps are subcommands of `python3 -I <root>/tools/entries.py`: `story-coverage`, `story-candidates`, `story-stale`, `story-wordings`, `story-wording-add`, `story-type-add`, `story-add`, `story-name`, `story-core`, `story-confirm` and `story-card`. `python3 -I <root>/tools/entries.py --help` prints the formats of the Story index, a Talking points file and a wordings file, and what each output line means, under *Stories*. The subcommands write `stories.md` and the wordings files, except a fix step 9 names; you write a Talking points file and a cue card as `--help` gives them, all but their `confirmed:` line.

1. **Coverage report.** Run `story-coverage --root <root>` and show the user its findings in a few lines. When it prints `core stories outside 3–5:`, propose entries to mark core when there are too few (speaking.md rule 9's high impact, complexity and personal involvement, judged from the entries, with `types per entry:` showing which already serve several types), or which to unmark when there are too many. On the user's yes, run `story-core <entry> on|off --root <root>` for each; an entry it prints `not indexed:` for gets core when its Story is indexed: in step 6, or with `story-add ... --marker core` now under a type the user confirms. A `story under too many types:` line that ends with the name hint (`if the section holds different Stories, name each with story-name`) may count several Stories of one section as one: read the section and each row's label and summary, and propose which rows tell the same Story and a name for each different one (a slug, `--help` under *Stories*, from what it is about, such as `origin` or `launch`; one name for rows that tell the same Story). On the user's yes, run `story-name "<question type>" <key> <name> --root <root>` for each row, and where a Talking points file lists that key in its `## Stories`, give that link the same title (`[<label>](../entries/<file>.md#<anchor> "<name>")`), so its lead keeps the key. For a pasted list from one interview, show the findings only: the core proposal is part of step 2's merge plan. Done when the findings are shown, the user has answered any proposal or passed, and each `story-name` the user said yes to printed `named:` or `already named:`; then go on to step 2 whatever they decided.
2. **Map each question to a type.** Run `story-wordings --root <root>` and propose the index type that covers the question, from the type names and the wordings it lists, and relay any `wordings type not in stories.md` or `wordings file with no type` line; the user confirms. A question no type covers gets a proposed new type, confirmed by the user and added with `story-type-add "<question type>" --root <root>` (on `FAIL: stories.md has this question type already: <type>`, use that type; on another `FAIL:`, propose another name). Once the type is confirmed and its row is in `stories.md`, keep the wording of a question the user brought (asked, pasted, or recalled from an interview), Talking points or not: `story-wording-add --root <root> "<question type>" "<the question, word for word>"`. Only a question the user brought keeps a wording; one you predicted is not one. Done when the type is confirmed and, for a question the user brought, the tool printed `added:` or `already kept:`.
   - **A pasted list from one interview:** map every question first, then run `story-coverage --root <root>` with one `--type <question type>` per question, and `--interviewers <n>` when the stage's number of interviewers is known (the recruiter's mail, the prep file or the user). Relay an `interview plan leads with fewer than 3 stories` line with Stories to add, so that about five lead the list (speaking.md rule 10), and any `story carries too many questions in one interview` line with a proposal of which questions should lead with another Story, or, when the line ends with the name hint and the questions tell different Stories of that section, names as step 1 says. Then make the **merge plan**, before any question's own steps: the questions merged onto 3–5 core Stories plus gap fillers (speaking.md rules 9–10), the leads drawn from `story-candidates` for each type.
     - One row per question, in the list's order: the question, its type, its lead with a rating (`strong`, `usable` or `weak`, and why in a few words), and a backup. A `weak` lead gets a backup that is stronger, or the note that step 4's recall prompts look for one.
     - The **switch rule**, one line for the whole plan: one interviewer hears a Story once; across interviewers a Story may repeat. A row's backup is what the user tells when this interviewer has already heard its lead.
     - The **common types**: the question types this stage commonly asks (a most technical project, a failure, a conflict; from the interview's research when there is one) that no question in the list maps to, each with a row of its own, which the user keeps or sets aside.
     - Step 1's core proposal: the Stories the plan leans on most, to mark core with `story-core` on the user's yes.

     The user confirms or changes the plan; rerun `story-coverage` with `--type <question type>=<key>` for each row's lead and the same `--interviewers` (each key as `story-candidates` prints it, the name included), and settle any `story carries too many questions in one interview` line it prints by changing rows. With an interview in prep (a `prep-<stage>.md` in the application folder), write the confirmed plan into its `## Decisions`: one row per question (decision: the question; value: the lead and its rating; source: `(user, <the day the plan was confirmed>)`; backup / note: the backup) and one for the switch rule (decision: `switch rule`; value: its line); with none, the plan lives only in the chat, so this run's last message shows it in full (see *Done when* below). Done when the user has confirmed the plan and, with an interview in prep, its rows are in `## Decisions`. Then take the questions one at a time, in the list's own order, steps 3–8 each. When step 4 changes a lead, update its row (and its `## Decisions` row) and rerun `story-coverage` as above.
   - **A story to keep, with no question** ("this is a good story, keep it"): propose the types it answers; for each type the user confirms, run steps 5–7, and step 8 only when the user wants Talking points.
3. **Staleness check.** When the type's row links a Talking points file, run `story-stale <the file the row links> --root <root>` before using it. On exit 1, show each change (`--help`, under `story-stale`, says how to diff it) and ask the user whether the Talking points still hold: reconfirmed as they are, run `story-confirm <the file> --root <root>`; otherwise revise them in step 8.
4. **The brief.** Show the question's brief, its parts in this order, in one message:
   1. **What it tests:** what the question checks and how an interviewer probes it. When the application folder has a `research-<stage>.md` for the stage in prep, from its `## Rubric`: the value or principle the question maps to and what the employer says it asks of an answer, with its URL; when that section says none is published, or there is no research file, mark the brief `general reading, no published rubric`.
   2. **Recall prompts:** two to four questions that bring back experiences the Log may lack ("a time a plan you owned fell apart"). The user's recall is the first source of a lead, ahead of the candidates.
   3. **Candidates:** run `story-candidates "<question type>" --root <root>` and show, in its order, the Stories on its `talking points <n>:` lines (marked "confirmed") and `indexed:` lines, then the `not yet indexed:` and `pending:` lines whose facts could answer this question, marked "not yet indexed". Give each a one-line summary and its entry, then the lead you recommend and why (for a pasted list, the merge plan's lead).
   4. **Risks** of the recommended lead: attribution, above all for work an agent built; recency; one experience carrying too many questions; fit for the role.

   Ask: tell your own story (most often the right one: step 5 records it in the Log now), take the recommended one, use another of these, or talk through which to use. The user decides the lead, and may change the type (a new one is added as step 2 says); rate the chosen lead `strong`, `usable` or `weak`, with why. Done when the user has picked a Story, rated in its merge-plan row or, with no plan, in this run's last message; told another (it goes to step 5); or set the question aside.
5. **A Story the log lacks.** When the user tells a story no entry holds, its facts go into an entry: the existing entry for that experience, or a new one created as [log](log.md) step 1 creates one. Each fact goes in its section the same session, cited as [SKILL.md › Provenance](../SKILL.md#rules-for-every-mode) says for the user's words, with an excerpt of the turn ([excerpts.md](../excerpts.md)). Talking points only point at facts; a fact lives in its entry. An answer that contradicts the entry follows [SKILL.md › Current truth only](../SKILL.md#rules-for-every-mode).
6. **Index the chosen Story.** Run `story-add "<question type>" entries/<file>.md#<section anchor> --summary "<one line>" --root <root>`, with the anchor of the section that holds its facts (`## Decisions and trade-offs` is `#decisions-and-trade-offs`; on an anchor the entry lacks, `story-add` refuses and lists the anchors it has); `#pending` when its facts sit only in `## Pending`; `--story <name>` when that section holds other Stories too (a slug, as step 1 says; the key then carries the name); and `--marker core` when the user said yes in step 1 to marking this experience core and `story-core` printed `not indexed:` for it. Done when it printed `added:` or `already linked:`.
7. **Deepen.** Grill the user on the chosen Story, one question at a time, each with your own guess from the entry for them to confirm or correct. Ask only what the entry lacks for the telling and its first follow-ups: the user's own actions and attribution, scope (people, teams), the trade-offs weighed, how a result was measured, what went wrong, the lesson. Each answer goes into its entry section the same session, with its source as step 5 says. A reply that confirms your guess ("same as you guessed", "yes, that") is the user's statement of it: the fact cites the user's turn, and its excerpt keeps the paragraphs of your turn that the reply confirms ([excerpts.md](../excerpts.md) step 2). A likely follow-up and its answer go in the entry's `## Likely questions`. Done when the entry holds each of those, as a fact or as a `GAP:` the user could not fill.
8. **Talking points, and the cue card in an interview.** Draft both only from the entry as steps 5 and 7 left it. With an interview in prep (a `prep-<stage>.md` in the application folder), first write the Story's row of the stage's **cue card** (*The cue card* below), then offer Talking points for the type once, as the way to reuse the Story later; the user may decline. With no interview, Talking points only. Draft the type's file with the sections `--help` gives for a Talking points file, in its order (step 9's run checks the order and the cue-line count). What goes in them:
   - `order:` `result-first` for a senior or complex Story (speaking.md rule 5), else `chronological`: you propose, the user decides.
   - `## Stories`: two or three, in order of preference, each with when to lead with it; when a posting is known, recommend which to lead with for it. One file per type: an angle is a reason in this list, never a second file.
   - `## Opening`: the only full sentence, a headline that may lead with the result; a number in it links its entry section.
   - `## Cue lines`, in telling order: context (two lines at most), then the actions, most of the lines, each one thing the user did, said with "I", then the result, then the lesson. Each line is a few words and a link to the entry section that holds its facts, with no numbers, results or technical detail copied in. About 7 lines at most; detail beyond that moves to `## Likely questions`.
   - `## Follow-ups`: links to each chosen Story's `## Likely questions`.

   Show the Talking points draft and save it only when the user confirms it: write the file at the path `story-candidates` named on its `talking points:` line, then run `story-confirm <that path> --type "<question type>" --root <root>`, which writes `confirmed:` and links the row's type to the file. On `type differs:`, write the row's type in the file's `type:` line and run it again; relay `row links another file:` to the user, who picks which file the row keeps. Declined, no Talking points file is written; what steps 2, 5 and 7 wrote stays, and for a pasted list with no cue card the question's merge-plan row keeps the Story's opening line and its result, linked to the entry section that holds it, beside the lead (in `## Decisions`, its backup / note cell; with no prep file, the plan in this run's last message).

   **The cue card**: `cue-card-<stage>.md` in the application folder, one row per Story that leads a question of the list, in the form `--help` gives under *Stories*. Facts only, never a script: the user reads it for half a minute, closes it, and tells the Story.
   - Before the list's first row, run `story-card --root <root>` with the `--type` values of the merge plan's last `story-coverage` run and write the Markdown after its `scaffold:` line to the file, with the stage.
   - **A Story's row:** Leads, the questions it leads as the list words them; Key facts, two or three, each with its caveat; Task, one sentence of the user's role or goal (speaking.md rule 18); I did, the user's own actions; Result, with its caveat. Each section a fact comes from goes in the Story's Provenance row. A Story whose type has confirmed Talking points takes its facts from the entry sections that file links.
   - The line under the title: the answer order (speaking.md rule 17) and the standing reminders, such as the task sentence.
   - **Finder:** from the `finder:` and `wording:` lines, the question types and the key words that point to each Story; then a `gap` row for each common type of the merge plan that no Story answers.
   - **Self-drill:** one or two reworded, vaguer questions per Story, each with the Story it calls for.
9. **Close.** With a cue card, first show it whole, once every question of the list has its row or is set aside. On the user's confirmation (with their changes made), run `story-card --confirm <the card> --root <root>`, then `story-card --check <the card> --root <root>` until it prints `card: ok`: for a `row with no provenance` or an anchor line, add or fix the row's sections; for `entry changed since confirmed`, reread the rows that cite that entry against the change, show the user what changed on the card, and confirm again. Then build the full card's page from the file, as [pages.md](../pages.md) says, and add its row to the prep file's `## Pages`. Then run `story-coverage --talking-points --root <root>`. Fix these findings for the rows and files this run wrote: `index names a missing entry`, and the six about Talking points files (`row links a missing talking points file`, `talking points file no row links`, `talking points type differs from its row`, `talking points with no readable confirmed date`, `talking points sections out of order`, `talking points over 7 cue lines`; a fix to a saved file goes back to the user as step 8 says). Report the others. Then `python3 -I <root>/tools/sync.py commit "stories(<slug>): <what changed>" -- <file>...`, naming each file this run wrote, the wordings files, the prep file step 2 wrote, and the cue card and its page included, with the slugs of a pasted list comma-separated.
10. **Next up**, after step 9's commit: run the command [SKILL.md › Next up](../SKILL.md#rules-for-every-mode) gives, with `stories`.

Done when every question in the request has a confirmed type and a chosen Story (or the user set it aside, and the report says so), every fact the user gave is in its entry with its source, each Talking points draft is saved or declined by the user, a cue card (with an interview in prep) is confirmed, its `story-card --check` prints `card: ok` and its page is in `## Pages`, and the last `story-coverage` prints none of step 9's findings for what this run wrote. For a pasted list with no prep file, the last message shows the whole merge plan as it now stands, every row, the switch rule and any opening line and result step 8 kept, since nothing else holds it; a pointer to an earlier message does not count. The last message ends with the Next up block.

## Files

| Path | What |
|---|---|
| `stories/<question-type-slug>.md` | Talking points, one file per behavioural question type; its `stories.md` row links it. Written by [stories](stories.md) |
| `outputs/applications/<folder>/cue-card-<stage>.md` | One interview's cue card: a row of facts per Story, the finder, a self-drill and the provenance; the source of its pages. Written by [stories](stories.md) step 8 |
| `stories/wordings/<question-type-slug>.md` | The wordings of the behavioural questions the user brought, word for word, one file per question type, Talking points or not. Written by `tools/entries.py story-wording-add` ([stories](stories.md) step 2) |
