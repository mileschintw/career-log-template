# Mode: rank

Before this mode's first step, run the **Trigger check** in [SKILL.md](../SKILL.md); a subagent sent to one step starts at that step.

Sort a list of employers (a career fair roster, a job board export, a set of postings) into tiers the user can act on, and give each worthwhile one an opening line backed by the log.

1. **Load the rules.** Read `direction.md` in full: the role ranking, the `**Sorting order` line under Employer preferences, the Constraints, and What to emphasise, by target. Work authorisation decides what step 2 researches; the target roles decide which teams step 2 looks for and what step 3 measures domain fit against. When work authorisation is empty ([SKILL.md › Setup](../SKILL.md#setup)), no employer is ruled out by it, and the report says so. When the target roles are empty, use the areas the entries' tags show most instead, and say so in the report. For earlier contact, run `python3 -I <root>/tools/application.py prior "<employer>"... --root <root>` once with every listed employer: each one's `folder:` and `applications.md:` lines are its contact; read no more of `applications.md` than those lines.
2. **Research each employer.** Before researching, grep `outputs/reports/*-ranking.md` for each name and read the newest earlier ranking that has it: re-check its hard-constraint facts on the web (its authorisation language, its sponsorship record, where its roles are), since they gate the tier (with a `**Visa sponsorship needed:**` line naming a visa, the sponsorship record comes from *Sponsorship records* below instead), and carry the rest over with the URLs it cites and its date (`<fact> (<URL>, as of <earlier ranking's date>)`), not citing the report itself. Research a carried item afresh only when the user asks, or when the earlier ranking has a `GAP:` for it. For every employer with no earlier ranking, and for every item not carried over, look up from the web, citing each fact's URL, every item below:
   - what it builds, and which teams hire engineers in the user's target areas;
   - each hard constraint `direction.md › Constraints` answers: whether the employer meets it (for a visa the user needs, whether it sponsors that visa: its filing history from *Sponsorship records* below while Constraints has a `**Visa sponsorship needed:**` line naming a visa, else researched here, US H-1B filing history being public data; for a location, where the roles are). An empty constraint is not researched. Whatever Constraints says, note its **authorisation language**: the sponsorship, citizenship or export-control clearance wording on its postings and careers pages;
   - size and stage.

   **Sponsorship records,** while `direction.md › Constraints` has a `**Visa sponsorship needed:**` line naming a visa (H-1B or a green card): you, the agent that ran the mode (a subagent never does), run [fit.md › Sponsorship lookup](fit.md#sponsorship-lookup) step 1 before researching, for every listed employer, with or without an earlier ranking, and with `--again <the employer as its record: line names it>` for each employer the user has given a legal name or website for since its record showed none found, as that section's step 4 says. A `reuse:` line is a record already kept: neither carry over nor research that employer's filings. Each `lookup:` line is looked up as that section's step 2 says, by whoever researches that employer; a subagent returns its answers to you and writes no file. Then you do its step 3 with the answers, committing at once, and take each employer's filings from what its step 4 prints: a `record:` line with a URL is a fact with its URL; a `none found` one is a fact as printed, with its date, citing `outputs/reports/sponsorship.jsonl`; an `unanswered` one, or a `lookup:` line `add` kept an older record for, is a `GAP:` naming the sites tried, citing any older record `show` prints with its date; step 1 exiting 1, or `add` exiting 1 with no `bad:` line to fix, is a `GAP:` quoting the tool's line. These filings are things to check: step 3 gates on what the employer says (its authorisation language), never on them. Ignore a `wording:` line: the authorisation language covers it. With no such line rank runs no `need`; while the *Trigger check* printed `direction visa sponsorship: empty`, the ranking and its report still hold that section's step 1 empty-item line, once, as a note beside step 1's empty-item notes, never in an employer's row and not an item step 5 checks. Then any filing history a visa in work authorisation asks for is still researched, as the item above says: say so after the line.

   Read each page with a plain fetch. Only when the fetch fails (an error such as 403, or a page without its content: built by script, a bot wall) is the page a Browser capture: follow [browser.md](../browser.md) for it, its sessions opened as *Running it* says (the command prints the CLI's skill first), in a session with no `--profile` (a careers page needs no sign-in) named exactly `rank-<employer>` (the employer's name in lowercase letters and digits, each other run of characters one hyphen, with none at either end, as in `rank-acme-co` for Acme & Co.) and closed when that employer is done, so researchers working in parallel never share one.

   Each item, and each part of one (a team, a division, an office), ends in one of two forms: a fact with its URL, or a `GAP:` naming what was searched for and not found. Every employer gets every item in one of those forms, the size, stage and citizenship or export-control note included; an item not yet searched for has neither, so search for it before step 4.

   When the list is long, research in parallel with subagents ([subagents.md](../subagents.md)), each with a share of the employers; otherwise research one employer after another. Before starting them, run the check's `playwright-cli install --skills` line now if it printed one; its other playwright-cli lines wait until a reply needs a Browser capture ([browser.md › Check and install](../browser.md#check-and-install)). Each prompt's first line is `Read <root>/skills/career-log/modes/rank.md whole and do only its step 2, earlier rankings included, for these employers: <names>. Reply with every item for each employer, each a fact with its URL or a GAP:. For any lookup: lines given, do only step 2 of fit.md's section "Sponsorship lookup", in the Browser session named, and reply with one JSON line per lookup: line, answered or unanswered, in the format its step 3 gives. Steps 1 and 3 to 6 are the caller's: ask the user nothing, write no file, and leave .playwright-cli/ in place for the caller to delete. Open every playwright-cli session with the command in browser.md › Running it, which prints the CLI's skill first. Fetch each page you cite by its own URL first; when that fetch fails, take items 2 and 3 of browser.md's section "Fallback order" before any other page or API (a job board's posting API included) stands in for it; when you can use neither, reply for that page with this line, word for word: GAP: no content from fetch: <URL>. If you opened a playwright-cli session, end your reply with the line `playwright-cli skill: read, ends: <line>` that browser.md › Running it describes; else end it with "playwright-cli: not used".`, with `<root>` as an absolute path. After it come step 1's results, as data: the target areas (or the entry tags used in their place), the constraints with their values, and work authorisation's value, or `empty`; then the `lookup:` lines *Sponsorship records* gave for its employers, if any (after each one that ends `again <date>`, the line `<employer>: the user gave <that legal name or website>`), with a line `Browser session: rank-lca-<n>`, `<n>` the subagent's number from 1. The agent that ran the mode, never a subagent, does the rest of this step. Check every reply for both forms and for that last line before step 3, and compare the text after `ends: ` with the last non-blank line of `<root>/.claude/skills/playwright-cli/SKILL.md` (`.agents/skills/` likewise), read with your file tool; treat a reply without the line, or whose text differs, as unchecked (one ending `playwright-cli: not used` passes), and research again yourself every fact of its employers that came from a page a plain fetch cannot read. In every reply, a fact cited to an API or JSON endpoint (such as `api.ashbyhq.com`) with no `ends:` line and no `GAP: no content from fetch: <that page's URL>` line for the page it stands in for was never checked against that page: research it again yourself too. Research yourself what a reply left out and every `GAP: no content from fetch` ([browser.md › Check and install](../browser.md#check-and-install)), in the order [browser.md › Fallback order](../browser.md#fallback-order) gives; then, once every subagent has replied, delete `.playwright-cli/`.
3. **Score in the order `direction.md` gives.** Hard constraints first, as a gate: an employer that breaks one in `direction.md › Constraints` (it will not sponsor the visa the user needs, as it says itself: step 2's sponsorship records never gate; its roles need a citizenship or clearance the user lacks) is out, whatever else it offers. An employer whose roles need a citizenship or clearance that the work authorisation answer does not mention is not out: list the requirement in its row as something to check. Then the sorting order: the `**Sorting order` line under `direction.md › Employer preferences`. With no such line, or only a `GAP:`, it is empty, whatever else that section holds: score by domain fit against `direction.md › Target roles, ranked` (or the entries' areas, as step 1 says), then size and pay, and say in the report that the sorting order is empty. The section's other lines never put an employer out (only Constraints does): a preference (a kind of team) breaks ties; a line that would rule employers out or set a minimum is listed, in the row of each employer it may affect, as something to check; a career-fair lesson (which booths to visit first, queues, entry times) goes in the report as a note for the fair, not into the tiers.
4. **Write the tiers.** For each employer: tier, one-line reason, the evidence for each hard constraint, and for every employer that is not out an opening line and one question to ask them. Every claim about the user traces to an entry. An opening line:
   - names the entry to lead with, from `direction.md › What to emphasise`; run `python3 -I <root>/tools/entries.py list --root <root> --window <years>` once, `<years>` the window `direction.md › What to emphasise` sets for every target, else 5 ([../writing.md](../writing.md) › Recency), and lead with an entry or series its `outside window` lines name only when it is the only evidence for what the employer hires for (one on a `window unknown` line is inside);
   - is one sentence the user can say aloud at the booth, in the form "I <what the entry shows I did, with its result>, and I'd like to do that on your <team or product>", never an entry name or a list of keywords;
   - is written fresh from the entry's facts, read in the entry itself this run. Take nothing about the user from an earlier ranking, its opening lines included: step 2 carries over only employer facts.
5. **Show the ranking and stop.** Show the user the whole ranking, in full and unprompted, never a summary of it: for every employer its tier, reason, evidence for each hard constraint, and for every employer that is not out the opening line and the question, each written out. Before sending it, check it line by line and fix what fails: every employer on the list has its own row with a tier; every employer that is not out has its own complete opening line (never "same as above" or a variant described in words); every item and every part of one is a fact with its URL (or a `none found` sponsorship record, as step 2 says) or a `GAP:` (a line that says, in any language, that something was "not checked", "not re-checked" or "not researched" is neither, and fails); every hard-constraint fact carried over from an earlier ranking was re-checked this run (sponsorship records: step 2's `need` decides). Then wait for their reply. Apart from the sponsorship records step 2 keeps and the `direction.md` lines this step records, nothing is written to a file, committed or pushed before it: until step 6 the ranking exists only in your message. Apply their changes and show the result again if they changed anything. Their reactions to companies are direction: record them in `direction.md` as [SKILL.md › Direction upkeep](../SKILL.md#rules-for-every-mode) says (a hard constraint such as "I won't relocate" is the `config.py fields` item `other hard constraints`, so it goes through [setup › Changes](setup.md#changes), which commits it). Commit each line you write to `direction.md` yourself at once: `python3 -I <root>/tools/sync.py commit "rank(<event>): direction" -- direction.md`; step 6's commit leaves it out. A new hard constraint is a gate for this ranking too: research it for each employer as step 2 says and apply it as step 3 says before showing the result again.
6. **Save,** only after step 5, to `outputs/reports/<YYYY-MM-DD>-<event>-ranking.md` with the sources, and add the event's row to the table under `applications.md › Events and contacts`, right below its last row, its Source cell a link to the report. Then check and commit with one command, run on its own: `python3 -I <root>/tools/check_save.py --root <root> <report> --commit "rank(<event>): <n> employers"`, with `<report>` the file this step saved and `<event>` the event its name gives. It checks the row and commits only on `check_save: ok`, naming the report, and `applications.md` when its new row names the report (step 5 committed its `direction.md` lines), so this command is the save's one commit, done when it ends with `sync: ok`. On exit 1, do what each `fix:` line says, then run the same command again; on a `held:` line, act on each `check:` line, then run it again with `--checked` added; on exit 2, fix the path its line names. Each other file that differs from HEAD gets a `left:` line and stays uncommitted: commit a `direction.md` it names as step 5 says, leave a bulk change waiting for its yes as it is, and show the user any other, in the Next up block.
7. **Next up**, after step 6's save: run the command [SKILL.md › Next up](../SKILL.md#rules-for-every-mode) gives, with `rank`.

Done when every employer on the list has a tier with evidence for each hard constraint or an explicit `GAP:`, every employer that is not out has an opening line traced to an entry, and the event is in `applications.md`, committed by step 6's command ending with `sync: ok`. The last message ends with the Next up block.
