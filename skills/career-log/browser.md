# Browser capture

How to read a web source that shows its content only after its scripts run or the user signs in (a *Browser capture*, [GLOSSARY.md](../../GLOSSARY.md)). Read this before the first Browser capture of a session; `import-web`, `rank`, `interview`, `fit`, `write` and `scan` point here. A page a plain fetch can read needs none of it.

## Fallback order

Take the first that gives the page's content, and for a page past item 1, say in the step's output which one did:
1. **A plain fetch**, with the agent's own fetch tool. It fails when it returns an error status (403, 999), or a page without the content you came for: only a title or heading, an empty shell built by script (Ashby, Workday), a bot wall, a login page. When the fetch of a page you would cite fails, read that page with item 2 before using a search result or another page in its place.
2. **`playwright-cli`**, below.
3. **The agent's own browser tool**, if it has one, for a user who declined the install or a machine where the CLI cannot run.
4. **Ask the user** to paste the text, or to save the page or file into `sources/inbox/`, and say which page and what is needed from it.

## Check and install

The trigger check ([SKILL.md](SKILL.md)) prints playwright-cli's state for `fit`, `write`, `import`, `rank`, `interview` and `scan`; do its playwright-cli `next:` lines before the first `open`. When this session's check ran for a mode without playwright-cli, run `python3 -I <root>/tools/check.py import` first. The install is done when that check prints no `next:` line for playwright-cli but the `PATH` line (whose prefix every later command then carries) and `git status --porcelain` lists nothing under `.claude/`, `.agents/`, `.playwright/` or `.playwright-cli/` and no change to `.gitignore`.

A subagent installs nothing, the skill included: two installs at once in one checkout fail. The agent that starts subagents runs the check's `playwright-cli install --skills` line, if there is one, before starting them; the check's other playwright-cli lines wait until a reply needs a Browser capture. A subagent whose `playwright-cli --version` fails, or whose checkout has no skill file, moves to the next fallback, and where that is asking the user, it replies `GAP: no content from fetch: <URL>` for the page, word for word, so the caller can find it.

## Running it

- **Open every session with the CLI's skill.** That skill is the manual for every command here and the rest (`click`, `snapshot`, `find`, sessions), and one installed during a session is missing from your skill list until a later session. So every session, signed-in or not, starts with this one command, which prints the skill, then a line that shows it was printed, then opens the page:

  ```
  cd <root>; cat <root>/.claude/skills/playwright-cli/SKILL.md; echo "playwright-cli skill: read"; playwright-cli -s=<name> open "<url>"
  ```

  The same text runs in PowerShell and bash; use `.agents/skills/` for agents that read skills there, and add `--profile` and `--headed` only as *Sign-in* says. If `cat` reports the file missing, the skill was not read, whatever the next line says: close the session and go back to *Check and install* (a subagent goes to the next fallback, as that section says). The `cat` prints the whole file into your output: never pipe or redirect it (`head`, `tail`, `Select-Object`, `/dev/null`, `> $null`, `Out-Null`). Read what it prints before the next command, and use the commands the skill documents; before a task one of its `references/` files covers (`running-code.md` for `run-code`, `session-management.md` for sessions), `cat <root>/.claude/skills/playwright-cli/references/<file>` too (`.agents/skills/` likewise). This file adds the Log's rules, and wins where the two differ: the one `--profile` of *Sign-in*, only for a site behind a sign-in, never `--persistent`, with every sign-in kept inside that profile (*Sign-in*); in PowerShell, a quoted URL rather than `--%`.
- Run every command with the Log root as its working directory (`cd <root>` first, in the same shell command), subagents included: the CLI writes snapshots and other output to `.playwright-cli/` in the current folder, which `.gitignore` ignores at any depth. Write your own output files there too, as `.playwright-cli/<session name>-<what>.json`, unless the mode names another place. That folder is scratch, not part of the Log, so a subagent told to write no file may still write there. It holds page text: the session that ran the mode deletes `.playwright-cli/` once the mode no longer needs it, after any subagents have replied. Leave `.playwright/` in place: it holds the CLI's config (*Check and install*), and without it `open` looks for a Chrome that is not installed.
- Use one named session per job, `-s=<name>`, on every command, and close it when the job is done (`playwright-cli -s=<name> close`). Close only the sessions you opened, each by its name: `close-all` and `kill-all` end other runs' sessions too. A session opened without `--profile` keeps nothing on disk and shares nothing with another session, so parallel subagents each open their own, with names that differ.
- **Read a page** anyone can see, with no `--profile`: open the session with the command above, then `playwright-cli -s=<name> eval "() => document.body.innerText" --filename=.playwright-cli/<name>-page.json`. Quote the URL: PowerShell splits an unquoted one at `&`.
- **Write output to a file, never into the reply:** `eval <function> --filename=<path>` runs the function in the page, waits for the promise it returns, and writes the result to `<path>` as JSON (a string comes out as one JSON string), however large; read it back with a JSON parser. `run-code --filename=<path>` is the reverse: the file is the script to run: one Playwright function, `async page => …`, with no `;` after it. Put a script longer than a line in a file under `.build/` and run it that way, since shell quoting differs between PowerShell and bash. Page variables (`window.__cap`) last until the page reloads, so a long job can be started by one call and read by later ones.
- **Download a file** (a project's source archive, a PDF): put `async page => { const [d] = await Promise.all([page.waitForEvent('download'), page.click('<selector>')]); await d.saveAs('<path>'); return d.suggestedFilename(); }` in a file under `.build/` and run it with `run-code --filename`; the file lands at `<path>`.

## Sign-in

A site behind a sign-in is read through one browser profile per machine, outside the repo: `--profile="$HOME/.career-log/browser-profile"` (the same text works in PowerShell and bash). Every signed-in session opens with this one `--profile`, so every clone and worktree on the machine shares the sign-in (the CLI's `--persistent` keeps a separate profile per folder instead). A profile can be open in one session at a time, so run signed-in captures one after another, never in parallel subagents. Before the first signed-in capture of a site in a session, look on its page for the user's own account (their name, avatar or account menu, not a sign-in button): some sites answer a signed-out visitor with an empty result, not a sign-in page or a 401. Without it, do item 1; a run with no user present reports that source as skipped instead (item 3). When `open` reports the browser already in use for this profile, another session holds it, perhaps the user's own or another run's: tell the user, and open again once they say it is closed. Leave that session to its owner: never close, kill (`pkill`, `kill-all`) or attach to it, and never open with `--isolated` instead, which reads the site signed out.

1. **First sign-in to a site:** open a session named `signin` with the command in *Running it*, on the site's sign-in page, adding `--headed --profile="$HOME/.career-log/browser-profile"`. Tell the user a browser window has opened, that they sign in there themselves, and to say when they are done. The user types every password and code; the agent reads nothing from the sign-in. Then `playwright-cli -s=signin close`.
2. **Every later capture** opens with the same command and the same `--profile`, headless (no `--headed`), and finds the user still signed in.
3. **When a page shows the sign-in again,** a call returns 401, a listing comes back empty where the user expects content, or the headless page meets a challenge the headed one did not, close the session and repeat item 1. A run with no user present (a scheduled one) reports that source as skipped instead.

The sign-in stays inside the profile: no `state-save`, `state-load` or cookie commands, and nothing from them in a file. Requests go out as the CLI's browser does them, never disguised: at a CAPTCHA or any other challenge, stop and tell the user.
