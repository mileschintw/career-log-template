# Engine testing works in phases: features, a refactor, then tuning on cheaper models

An Engine change is tested in one of three phases, in order. In the feature phase, while the planned features are still being built, a change is tested on the model the session runs on, each test case run once, and it passes when the feature works and the user can use it. Once the features are done, the refactor phase moves the skill's deterministic steps, the ones a script can do the same way every time, out of the instructions and into tools. Only then does the tuning phase measure the rules on cheaper models: Haiku and Sonnet rounds of three runs per check, each on a different test case, with a stop rule that ends fixing by wording once a fix has targeted the same failure twice and it fails again. Tuning measures how well a model follows the text's rules, and while features are still landing, the next feature or the refactor rewrites that text and voids the runs made on it, so rounds spent before then are wasted. The refactor also takes rules out of the text: a step a tool does needs no wording a cheap model must follow, so tuning after it measures fewer rules, and only the ones that stay.

## Considered options

- **Keep the cheap-model bar throughout**: every change passes Haiku and Sonnet rounds before it merges. It catches weak wording early, but most of the wording it tunes is rewritten by a later feature or by the refactor, and each rewrite voids the runs.
- **Drop cheap-model tuning altogether**: test only on the session's own model. It costs less, but a strong model reads past ambiguous wording that still makes it fail now and then; cheaper models fail on that wording reliably, so they find it, and a skill tuned on them can also be run on them for less.
