# A session claims the Log files it writes

`sync.py commit` commits whole files, so a session that commits a file another session in the same checkout also edited takes that session's changes with it. #703 added a guard, `held()` in `tools/sync.py`: before committing, it refuses a changed Log file that another live run wrote. Who wrote a file is decided by `live_run()` in `tools/logfiles.py`: of the runs whose `.build/runs/<key>/live` marker was touched in the last `LIVE_HOURS` (2) hours (`live_runs()`), the file goes to the latest-started one whose start is at or before the file's time on disk. `tools/check.py` (`check_uncommitted()`) uses the same attribution for its `log change (live run <key>):` lines. Only `scan.py` makes a marker (`cmd_run()` in `tools/scan.py`, from write, fit and fit-several, and `cmd_touch()` when it makes a deleted one again), and `--run <key>` on `sync.py commit` (or `check_save.py --commit`) lets the caller's own run through.

#721 lists what that leaves open: an interview session and a fork start no run, so they are never seen; a fork's edits made during the main session's run count as that run's; and not every commit passes `--run`: SKILL.md › Commits says to add it in a run `scan.py run` started, and write.md step 10 adds it to `check_save.py --commit`, but the commit commands in fit.md and fit-several-postings.md do not. It asks which of two fixes to take: (a) every mode that writes Log files starts a run and passes `--run`, or (b) a per-session baseline of uncommitted Log files.

Attribution by time on disk cannot say which of two overlapping sessions wrote a file. A file has one time; `live_run()` gives it to the latest-started run, whoever wrote it last. In the incident behind #703, the pack session and the talk session both edited the pack file (`interview-<stage>.md`). Give each a run, the pack session's started first: when the pack session edits the file last, the file is put down to the talk session's run (checked against `logfiles.live_run()`), so the pack session is held from committing its own file, and the talk session, committing with `--run`, takes the pack session's hunk, which is the incident itself. #732 met the same limit from the other side: a save in one session was held because another session's run had started earlier, and `check_save.py` now passes the files it saved as `--take`.

So the Engine records ownership per session, by name, not by time:

- **A session key.** The *Trigger check* prints `session: <key>` the first time it runs in a session, and writes `.build/sessions/<key>/`. A later check in the same session passes `--session <key>` and keeps it, as the first `mode start:` value is kept. A session is live while it holds claims, and idle once it has released them all; an idle session keeps its key, so a later mode in the same session goes on with it. Next up (`check.py done --session <key>`) releases every claim of the session. A session that closes without Next up does the same with `sync.py end --session <key>`, which replaces `scan.py end <run>`: a session of a multi-session interview run that hands its phase on, and a mode run unattended (`CAREER_LOG_UNATTENDED`), which runs no Next up ([SKILL.md](../../skills/career-log/SKILL.md) › *Next up*).
- **No routine question to the user.** Time never releases a claim, and no check asks whether a session has ended. A session that crashed or was closed with claims still held keeps them, unnamed, until another session wants one of its files. Only then does the `next:` line under `owned:` or `held:` ask the user whether that session is still going; when they say it has ended, `sync.py end --session <its key>` releases its claims. So a long talk session that runs no tool for hours loses nothing, and the user is asked at a real conflict and nowhere else. Both rules are the maintainer's decision of 2026-11-13: Next up releases the claims, with no routine question (no stream of questions that each need their yes), and a session that ended without Next up is asked about only at a conflict.
- **A baseline.** That first check records, under the key, the hash of each uncommitted Log file it found. Those files are not the session's: `claim` and `commit` refuse them until they are settled through the steps the check already prints (the user's yes). The hashes tell a later check that such a file is still changing, so another session is still writing it.
- **Claims.** Before its first edit of a Log file, a session claims it: `sync.py claim --session <key> -- <file>...`. A file another session has claimed is refused with an `owned: <file> (session <other key>)` line and a `next:` line: hand the rows to its owner, or, when the user says that session has ended, release its claims as above. A claim lasts until the session's Next up or its end; `sync.py release --session <key> -- <file>` hands a file on, as a brief's *You own:* line does.
- **The commit.** `sync.py commit --session <key>` (and `check_save.py --commit`) claims each path it names that nobody holds, and holds a path that another session has claimed or that is in this session's baseline and not yet settled: `held: <file> (session <other key>)`, with the `next:` line `held()` prints today. While another session holds claims, a commit without `--session` stops with a `next:` line that names the flag and the *Trigger check*'s `session:` line, so a mode's commit command need not spell the flag out. `settle commit --session <key>`, run on the user's yes, is how a baseline file is settled; like `commit`, it holds a path another session has claimed. A baseline entry lapses, in every session's baseline, once its file matches HEAD.
- **The upgrade mode** takes no key. It has no *Trigger check* ([upgrade.md](../../skills/career-log/modes/upgrade.md)), and until its step 3 replaces the Engine it runs the Log's old tools, which may predate sessions. Its own commits (the plain `git commit`s of steps 2 to 5) claim nothing, so its several end points (step 2's `OK:`, a `stop:` or `error:` the user does not settle, and the others) need no `end`. A mode one of its guides starts (setup, say) commits as usual on the new Engine (step 3 item 2). upgrade.md does not say today that such a mode runs its *Trigger check*; it will, and that mode then takes the key the check prints like any mode. Its Next up releases its claims, and a claim it leaves is asked about only at a conflict, as above.
- **The check.** `log change (session <key>):` lines replace `log change (live run <key>):`: the files another session has claimed, kept out of every settle, with no question about that session. An uncommitted file that nobody claimed is offered to the user as an earlier session's, as now. A baseline file whose hash changed since this session's first check gets a note that another session is still writing it.

A run keeps its folder, its capture paths, its Browser sessions and the seven-day pruning (`cmd_run()`); it no longer marks files as its own. `scan.py run` takes `--session <key>` and records it in the run folder, so that for one release `--run <key>` can stand for the session that started the run; then `--run` goes.

A subagent works inside its session: its writes are the session's, in the folder [subagents.md](../../skills/career-log/subagents.md) gives it. A fork is a session of its own and must not use its parent's key, which it can read in the conversation it inherits. A fork started from a brief ([interview-sessions.md › Brief for a new session](../../skills/career-log/modes/interview-sessions.md#brief-for-a-new-session)) is told so by a line of the brief: run the *Trigger check* without `--session` and use the key it prints. A fork the user makes without a brief may keep the parent's key. [interview-sessions.md](../../skills/career-log/modes/interview-sessions.md) has a fork that owns no file write nothing, and a fork that needs a file be given it first, by its owner or the user; the line that gives it the file (a rule this decision adds there) also tells it to run the *Trigger check* without `--session` first. A fork given a file without that line claims it under its parent's key, and the guard does not stand between the two.

[interview-sessions.md › One writer per file](../../skills/career-log/modes/interview-sessions.md#one-writer-per-file) stays the rule; claims are how the tools hold to it. A brief's *You own:* line is the files the starting session releases and the new one claims; the `git -C <root> status --short` check before committing stays, and a held file replaces asking the user whether its owner has finished. Its *Which checkout* section is the reason the guard is needed at all: sessions in separate worktrees share no files.

What it costs:

- **Tools.** `tools/logfiles.py` gains the session record (key, baseline, claims) and loses `live_run()`, `live_runs()`, `write_live()`, `read_live()` and `LIVE_HOURS` (also named in `check.py`'s and `scan.py`'s docstrings); `tools/check.py` prints the key, writes the baseline, prints the new lines, names no session as possibly ended, and releases the session's claims in `done`; `tools/sync.py` gains `claim`, `release` and `end`, `--session` on `commit` and `settle commit`, and `held()` reads claims; `tools/check_save.py` passes `--session` and its saved outputs are claimed rather than passed as `--take`; `tools/scan.py` stops writing the run's live marker, drops `run --touch` and `end`, and records the session key a run is started with. Their tests change with them: `tools/tests/test_sync.py` (its live-run cases), `test_check_save.py`, `test_check.py`, `test_scan.py`, `test_logfiles.py`. `.build/` is not Log data, so no Log needs an upgrade.
- **Skill text.** [SKILL.md](../../skills/career-log/SKILL.md) › *Trigger check* (the `session:` line, kept like `mode start:`) and › *Commits* (claim before the first edit; `--session` replaces the `--run` sentence; *What an earlier session left* names `log change (session <key>):` lines instead of a run still going), [upgrade.md](../../skills/career-log/modes/upgrade.md) step 3 item 2 (a mode a guide starts runs its *Trigger check*), [SKILL.md](../../skills/career-log/SKILL.md) › *Next up* (`--session` on `check.py done`, and `sync.py end` for an unattended run, next to its rule that such a run runs no Next up), [log.md](../../skills/career-log/modes/log.md) step 5 (its own `check.py done log`), [write.md](../../skills/career-log/modes/write.md) steps 1, 9 and 10, [fit.md](../../skills/career-log/modes/fit.md) › *Capture a posting* and step 8, and [fit-several-postings.md](../../skills/career-log/modes/fit-several-postings.md) step 1 (their `scan.py run`, `--run`, `--touch` and `end` lines), [interview-sessions.md](../../skills/career-log/modes/interview-sessions.md) (claims under *One writer per file*, a *Session:* line in the brief, `--session` on its `check.py done interview`, and `sync.py end` in *How each session ends*). No other mode file changes: the claim rule is one sentence in *Commits*, and a commit without the flag is stopped by the tool.
- **What it does not catch.** A session that edits a file without claiming it, while another session also edits it unclaimed, is not held: the first commit claims and takes both. Nor is a fork that writes under its parent's key (above). And a session that crashed with claimed files left uncommitted keeps them out of every settle, unnamed, until another session wants one of them: that is the price of asking the user nothing routinely. A session that claims is safe from every other session that claims or commits under its own key.

## Considered options

- **(a) Every mode that writes Log files starts a run and passes `--run`.** Nearly no tool change: `held()` and `check_save.py --run` already work. But it keeps attribution by time on disk, which is wrong whenever two runs overlap, the one case the guard is for (above). It also costs the most skill text: a run start and a `scan.py end` in every writing mode, `--run` on the commit commands of every writing mode (18 skill files carry a `sync.py ... commit` command: SKILL.md, commits.md and 16 mode files; only SKILL.md › Commits and write.md's save name `--run` today), and `run --touch` wherever a session can go two hours without one, since only write step 9 touches the marker today and an interview session often runs longer; and a marker left to expire releases a run's files on a timer, whether or not its session is still going. A fork would still read its parent's run key.
- **(b) As #721 states it: a baseline of the uncommitted Log files at the session's start, and a commit that holds a file whose content changed in a way the session did not make.** The baseline tells the files a session found from the ones it did not, but not its own edits from another session's made later: two sessions that both start with a clean pack file and both edit it look the same to each. The decision above is this option with claims added, which name the writer instead of inferring it.
- **Leave it to the written rule** of interview-sessions.md and the agent's `git status` check before each commit: no tool change, and the incident happened under the same kind of care, with the user sequencing the two sessions by hand.
