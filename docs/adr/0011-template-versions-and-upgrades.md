# Template releases carry a version and an upgrade path

A Log made with "Use this template" has no history in common with the Template, so it cannot merge a newer one, and a change to the Log's data format (entry front matter or sections, a `config.toml` field with no default, a `direction.md` section, the `outputs/applications/` layout, a `stories.md` mark) breaks it. So every publish of the Template is a release: a semver tag `v<version>` on the public repo and a GitHub Release, and the export stamps `tools/TEMPLATE_VERSION` with two lines, the version and `source <commit>`. A release that changes a Log format is **breaking** and ships an upgrade guide; one that changes only the Engine is not, since an upgrade replaces the Engine whole. While the version is 0.x, a breaking release raises the minor number and any other the patch; the maintainer decides when to release and which version it gets, and the agent only proposes one. An export made without a version (CI, a test) is stamped `next`, which no Log upgrades from or to.

The guides live in the Engine, at `docs/upgrades/upgrade-<version>.md` with a script `upgrade-<version>.py` for what is mechanical, so fetching a release's tag brings every guide up to it. The guide of the release not yet made is `upgrade-next.*`: each pull request that changes a Log format adds its step there, and each that adds a setting with a default (a Config field, a Direction item) its question under `## 3. New settings`, which ships the guide in a patch release (#329), and the release renames it to its version and starts a new one from `upgrade-skeleton.*`; the export ships neither, and refuses a versioned export while `upgrade-next.*` holds a change or a new setting. The maintainer's scratch Logs that test a guide (`test-<version>.sh`) stay out of the export too. Each guide's assets are also attached to its Release, for a Log whose Engine has no upgrade mode yet.

The upgrade mode runs the target release's own tool and mode text (`tools/upgrade.py`, `modes/upgrade.md`), fetched from its tag with git, so a fix to the upgrade reaches a Log on its first upgrade after the fix, whatever Engine it has. It goes one release at a time: each release whose guide exists is a step, then the target, and each step replaces the Engine with that release's and runs that release's guide, on the Engine the guide was written and tested against, in its own commit. The user's yes comes once, on the whole upgrade; until then nothing is pushed, and a no can reset to the commit the upgrade started from.

Before 0.1.0 the stamp held only the exported commit, and older Templates had none. 0.1.0's commit is the only one that names a release; every other commit, or no file, means a Log from before 0.1.0, which follows the 0.1.0 guide first (written for any older Template), then the mode.

We considered a manifest of file hashes, written at install, to find the Engine files a user changed, as installers outside git must keep. A Log is a git repo and every release is a tag, so the tag of the Log's version is that manifest: `git diff` against it names the files the Log edited, added or deleted, and the same tag is the base for merging the user's edits into the new Engine. The upgrade overwrites the Engine and keeps a file the Log added; it then offers, file by file, to merge the Log's edits back with `git merge-file`, showing each hunk, and stops on a conflict for the user to settle. Its backup is the commit it started from, which it requires to be clean. The Log's own `.gitignore` lines go back with no question, as 0.1.0's guide does. A Log from before 0.1.0 has no tag to diff against, so its edited Engine files are not found; its guide says so.

We considered fetching guides from the Release assets (`gh` or a ZIP) and rejected it: it needs a second channel beside the tag the Engine comes from, and `gh` with a login for a public read. And we considered one jump to the target, running every guide in between on the newest Engine, and rejected it: a guide's script calls the tools of its own release, and nobody tests it against later ones.
