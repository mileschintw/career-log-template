# Upgrade a Log made before 0.1.0 to 0.1.0

For the agent of someone whose career-log Log was made from the Template before 0.1.0 (any commit of https://github.com/mileschintw/career-log-template before `ce73717`, the commit tagged `v0.1.0`). Follow it with the user, in order. It works whether or not the Engine has already been replaced with 0.1.0's: a Log in that state fails every mode at `config: missing`, and step 3 is what fixes it. Talk to the user in their language; the files stay in the Log's record language.

The release holds two files: this guide, `upgrade-0.1.0.md`, and `upgrade-0.1.0.py`, a script that prints, one line each, what the Log still has in an old format, and makes the mechanical changes with `--apply`. Each line starts with its kind: `apply:` the script's `--apply` makes the change (the line names which), `migrate:` you make it by hand, `ask:` the user decides, `review:` you show it to the user, who may keep it as it is, `later:` it waits for a later mode, `done:` the script changed it.

Placeholders: `<root>` is the Log's root (`git rev-parse --show-toplevel` in the Log). `<py>` is `python3` on macOS and Linux, `py -3` in Windows PowerShell, until step 2 names another. `<default>` is the default branch (`git -C <root> symbolic-ref --short refs/remotes/origin/HEAD`, minus `origin/`). Commit with the Log's local git identity (`git -C <root> config --local user.email`); when none is set, ask the user for theirs and set it, as `SETUP.md` step 3 does.

Which steps run where: steps 0, 1, 3, 4 and 5 run once per Log, on one machine. Step 2 runs on every machine, and its playwright-cli skill on every clone where the user wants playwright-cli. Another machine or clone, after the upgrade is pushed: `git -C <root> pull --ff-only`, the script downloaded as step 0 item 2 says (step 2 item 1 runs it), then step 2, then step 5's items 1, 2 and 5.

## 0. Start

1. `git -C <root> status --short`. A ` M tools/askpass-macos.sh` line whose `git -C <root> diff -- tools/askpass-macos.sh` shows only `old mode 100644` and `new mode 100755` is 0.1.0's setup making that file executable: restore it with `git -C <root> checkout -- tools/askpass-macos.sh`, with no question, wherever it shows up in this guide. A `?? config.toml` line is 0.1.0's setup's answers: keep it, with no question; step 3's commit takes it. If it lists other files, show them to the user, and wait for their answer: commit them or discard them before the upgrade. Then `git -C <root> pull --ff-only`. When the pull refuses because it would overwrite the untracked `config.toml` (another clone committed one), show the user the lines where it and `git -C <root> show origin/<default>:config.toml` differ, and ask which file to keep; move the untracked file out of the Log, pull, and, to keep the untracked one, copy it back over the pulled one (step 3's commit takes it).
2. Download the script into `.build/`, which every Template's `.gitignore` leaves out:
   - macOS and Linux: `mkdir -p <root>/.build/upgrade && curl -fsSL -o <root>/.build/upgrade/upgrade-0.1.0.py https://github.com/mileschintw/career-log-template/releases/download/v0.1.0/upgrade-0.1.0.py`
   - Windows PowerShell: `New-Item -ItemType Directory -Force <root>/.build/upgrade | Out-Null; curl.exe -fsSL -o <root>/.build/upgrade/upgrade-0.1.0.py https://github.com/mileschintw/career-log-template/releases/download/v0.1.0/upgrade-0.1.0.py`
3. Run it: `<py> -I <root>/.build/upgrade/upgrade-0.1.0.py <root>`. It exits 1 while it prints lines to act on, and 0 with `OK: nothing left to migrate`. It needs Python 3.9 or later here; `--apply log` (step 3) needs 3.11, which step 2 installs.
4. **`data/` branches.** For each `ask: branch … data/<topic>` line (left from the old *Bulk changes as pull requests*), settle the branch now, before anything changes the working tree: show the user `git -C <root> log --oneline origin/<default>..origin/data/<topic>`, say that closing drops those commits' changes, and ask merge or close.
   - Merge: its pull request with `gh pr merge <n> --merge` when it has one (`gh pr list --head data/<topic>`), else `git -C <root> merge --no-ff origin/data/<topic>` and push; then `git -C <root> pull --ff-only`.
   - Close: `gh pr close <n>` when it has one (a Log with no GitHub remote has none).
   - Then delete it: on the remote (`git -C <root> push origin --delete data/<topic>`), locally if `git -C <root> branch --list data/<topic>` shows it (`git -C <root> branch -D data/<topic>`), and its worktree if `git -C <root> worktree list` shows one (`git -C <root> worktree remove <path>`).

Done when the script has run, and a new run prints no `ask: branch` line. A `migrate: poppler:` line is step 2's.

## 1. Engine

Do this step when the script prints a `migrate: engine:` line or an `apply:` line that names `--apply engine`. Otherwise go to step 2. When it printed an `apply:` line naming `--apply engine` and no `migrate: engine:` line, the Engine is already 0.1.0's: skip item 1 and start at item 2.

The Engine commit in item 3 goes straight to the default branch. `AGENTS.md › Changes` sends an Engine change through a pull request so that the user reviews a change to how the agent works; this commit is the upgrade itself (the released 0.1.0 Engine, or only the Log's own `.gitignore` lines put back), the user says yes to it in item 3, and steps 2 to 5 need it in place. Its message body says so, so that `AGENTS.md`'s rule for an Engine commit on the default branch (revert it) is not applied to it later.

1. When it printed `migrate: engine:`, tell the user that the Engine paths below are replaced by 0.1.0's, so an Engine file they edited themselves is overwritten (git history keeps their version). On their yes:
   ```
   git -C <root> fetch https://github.com/mileschintw/career-log-template.git refs/tags/v0.1.0
   git -C <root> checkout FETCH_HEAD -- skills tools SETUP.md AGENTS.md CLAUDE.md GLOSSARY.md docs .gitattributes .gitignore .github entries/_template.md
   ```
   The Log's own files (entries, `README.md`, `direction.md` and the rest) are not among these paths. On their no, the upgrade stops here: 0.1.0's formats need 0.1.0's Engine.
2. `<py> -I <root>/.build/upgrade/upgrade-0.1.0.py <root> --apply engine`. It deletes the Engine files 0.1.0 removed and appends, under a `# This Log's own lines` header, the Log's own `.gitignore` lines (comments included), the ones no Template had, which the checkout overwrote. Its `done:` lines are this step's result; the check it prints after them is step 3's work.
3. Show the user `git -C <root> status --short` and the `done:` lines, then on their yes: `git -C <root> add -A -- skills tools SETUP.md AGENTS.md CLAUDE.md GLOSSARY.md docs .gitattributes .gitignore .github entries/_template.md` (the same paths whether or not item 1 ran), commit as `engine: Template 0.1.0` (also when only `.gitignore` changed) with the body `The upgrade to the released Template 0.1.0 (upgrade-0.1.0.md), not an Engine change to review.`, and push.

Done when a new run of the script prints no `migrate: engine:` line and no `apply:` line naming `--apply engine`, and `git -C <root> status --short` lists no Engine path.

## 2. Machine setup (every machine)

0.1.0 replaces the old step 5 of `SETUP.md` (the LaTeX toolchain) with *Machine setup*, which also installs Python 3.11 or later, poppler and, if the user wants it, playwright-cli; its table lists what each piece installs.

1. **poppler first, on every Mac** (and on Linux when `pdftotext -v` fails and the user cannot run `sudo apt-get install poppler-utils`); the script's `migrate: poppler:` line points here. 0.1.0's setup takes poppler from Homebrew, installing Homebrew first behind two password dialogs; on a macOS version Homebrew no longer builds packages for (macOS 14, for one), `brew install poppler` compiles about 70 packages from source for hours and can fail. Setup takes that route only when it finds no poppler, so poppler goes in first, without Homebrew:
   - **The user's own poppler** (Homebrew's, MacPorts', or one they built): on PATH or in Homebrew's folders, the script finds it and installs nothing. Elsewhere, ask the user for its `bin` folder (the one holding `pdftotext`) and run `python3 -I <root>/.build/upgrade/upgrade-0.1.0.py --poppler <folder>`, which makes it findable from `~/.local/bin`.
   - **Otherwise** `--poppler` alone installs conda-forge's ready-built poppler, for this user only, with no dialog (45 to 60 MB to download, about 230 MB on disk, a minute or two). Tell the user so, then run it as a background command and wait for it to end: `python3 -I <root>/.build/upgrade/upgrade-0.1.0.py --poppler`.

   Then:
   - It ends with `OK:` (installed, in place, or `poppler is already here`): go on to item 2.
   - It ends with `failed:`: show the user that line, fix what it names with them (a failed download is the network: offline, or a proxy, which `HTTPS_PROXY` sets), and run it again. On macOS, setup (item 2) runs only once it ends with `OK:`; before that, setup would take the Homebrew route above. When it cannot be fixed now, go on to step 3 only if `python3 --version` already says 3.11 or later (steps 3 and 4 need Python, not poppler), and come back to this item before step 5.
2. Run `SETUP.md` step 5 whole, from the Log's own (now 0.1.0) `SETUP.md`: its item 1 asks the user about playwright-cli, its item 2 is the warning before an administrator dialog, and the script runs in the background. On macOS and Linux, start it as `PATH="$HOME/.local/bin:$PATH" sh tools/setup.sh …`, so that it finds item 1's poppler and installs no Homebrew; once item 1 ended with `OK:`, a Mac opens no dialog, so item 2's warning is for Windows only. Every later setup run, such as one a `next:` line names, keeps that `PATH=` prefix. When the user said no to playwright-cli, run the script twice: first with `--no playwright-cli` (`-No playwright-cli` on Windows), which only records the answer and installs nothing, then with neither. A run that installs ends with `tools/check.py setup`'s lines; a run that printed none of them installed nothing. Steps 1 to 4 of `SETUP.md` (prerequisites, clone, git identity, skill link) are unchanged in 0.1.0: run one only when its check fails. In step 2's eol check, a binary file's `i/-text w/-text` passes too, and so does `w/none` on a one-line file with no line end.
3. **A shell that was open before the script** (an agent's session) does not see what it installed. On macOS and Linux, put `export PATH="$HOME/.local/bin:$PATH";` before every command from here on; on Windows, the `$env:Path = …` line the script prints last. Then run `<py> -I <root>/tools/check.py setup`. When it prints `python: too old` and `next: run this check again with <python> in place of …`, that `<python>` is `<py>` from here on.
4. When `git -C <root> status --short` lists ` M tools/askpass-macos.sh`, restore it as step 0 item 1 says.

**When the check fails:** a `next: now, for tinytex` line with `pdftotext: missing` above it is poppler: on macOS, run item 1 again, not setup; on Linux, give the user the `sudo apt-get install poppler-utils` line it names, and run item 1 only when they cannot. For any other `next: now` line, do what the line says. Steps 3 and 4 may go on while poppler is all that is missing (`python: ok` holds); step 5 needs it.

Done when `SETUP.md` step 5's check holds on `<py> -I <root>/tools/check.py setup`'s output, its last line is `next: go on with the mode` and every other `next:` line is a `next: now, for playwright-cli` line saying `(the user declined playwright-cli)`, and, unless the user declined playwright-cli, it prints no `playwright-cli skill: missing (this checkout)` line. Its `config: missing` line is step 3's work, and so are a `log change: ?? config.toml` line and the `next: now, first: settle the files above` line it brings, when `config.toml` is the only file listed.

## 3. Log formats

1. `<py> -I <root>/.build/upgrade/upgrade-0.1.0.py <root> --apply log`. It makes every change an `apply:` line named, then prints what is left. Among them, it deletes the Template's `GAP:` question lines from `direction.md`, with any `(skipped, user, <date>)` note on them: 0.1.0 records no skip, and step 4 shows such an item as empty, for the user to answer or leave. When the Log has no `config.toml`, it writes one with `tools/config.py init`, every field at its default. When 0.1.0's setup already wrote one, it leaves that file as it is and prints nothing about it. Note which it was (a `done: config.toml written` line or none): item 2's Languages line and step 4 depend on it. Either way, with it in place, the setup mode in step 4 goes to *Advanced*, which shows the current values, and not to *Quick*, which would ask again what `direction.md` already answers.
2. **Every `migrate:` line,** yourself, as the line says:
   - **The old Languages line:** when item 1 wrote `config.toml`, `<py> -I <root>/tools/config.py set record_language "<language>"` when its record language is not English. When `config.toml` was there before, its `record_language` is the user's newer answer to 0.1.0's setup: leave it when it names the same language as the old line, and otherwise put the two in item 3's message (which record language to keep; preselected: `config.toml`'s), setting the old line's with that command only when the user picks it; an output language it names (`cover letters in German`) stays under `## Writing preferences for applications` as its own line with the old line's source, date unchanged (`- Cover letters in German (user, 2026-05-02)`); then delete what is left of the line.
   - **A `**Target roles:**` line with an answer:** a numbered list under `## Target roles, ranked`, best first, one role per item, each with the source the line had (`1. Backend engineer (user, 2026-05-02)`).
   - **`## Career-fair tactics` with lines:** each lesson goes under `## Employer preferences`, where 0.1.0 keeps career-fair lessons for `rank` to read before the next fair (`skills/career-log/SKILL.md › Direction upkeep`), as one line starting `At a career fair:`, with the lesson's words (its first letter lowercased) and source unchanged (`- At a career fair: visit the two largest booths first: queues pass an hour after noon (user, 2026-04-20)`); then delete the section.
   - **`profile.md`'s work authorisation:** when `direction.md › Constraints` has no `- **Work authorisation:**` line, move the answer there with its source; then replace the profile line with the one `tools/template/profile.md` has.
   - **`tools/entries.py check: no README row` or `README row …`:** add or fix the entry's row in `README.md › Entries` from its front matter, the rows newest first by the start of their period (0.1.0 sets no order; this one reads best), with a status from `skills/career-log/SKILL.md › Layout`: `imported` when its facts cite files in `sources/` or the user's repos, `stub` otherwise (an entry mostly `GAP` or empty, or holding only a few `(user, …)` lines).
   - **No visibility line:** add `visibility: GAP` to the entry's front matter.
   - **A tool that failed** (`tools/config.py init failed`, `cannot read stories.md`, `tools/entries.py check failed`): show the user the error it quotes, fix the file it names with them, and run the script again.
3. **The `ask:` and `review:` lines,** in one numbered message, so the user can answer every item at once, each with its preselected answer:
   - **`GAP: confirm:` lines** (a value an old import found and nobody confirmed): confirm it or drop it. Preselected: drop. A confirmed value goes into its section in 0.1.0's form with `(user, YYYY-MM-DD)`, today's date; either way the `GAP: confirm:` line goes.
   - **`visibility: public` entries:** before 0.1.0, `public` was the default, so it does not show that the user chose it. List each entry by its title: public, private or nda? Preselected: public. Write each answer as `visibility: <answer>  # (user, YYYY-MM-DD)`, the comment being how the script knows it was asked.
   - **`stories.md › Application questions` rows with no Scope column:** the scope you would give each row (`shared`, `per-angle` or `per-company`; `per-angle` when unsure), as 0.1.0's comment there defines them. Preselected: yours. Then rewrite the section as `tools/template/stories.md` has it (its comment and columns), with the Log's own rows only; a row's old answer link goes into the Approved answer column, written `general: [answer](<path>)` in a `per-angle` row. Answer from and User's direction stay empty in the old rows: the write mode fills them when it first answers that question type.
   - **`review:` an edited front page that still has the old Template's text:** replace it with `tools/template/README.md` (and `README.zh-TW.md`) keeping the Log's `## Entries` section, cut the old Template's lines, or keep it. Before asking, run `<py> -I <root>/.build/upgrade/upgrade-0.1.0.py <root> --old-lines`: it lists, as `<file>:<line>: <text>`, each line of the page that came from the old Template and 0.1.0's page lacks, and cut deletes those lines, plus what the mending below leaves empty. In the question, say how many lines cut deletes and under which headings; when the Log's history holds the old Template's page, the list is every old line 0.1.0 reworded or dropped, often feature descriptions, *How to use* rows and the file list too, besides the old settings. Cut keeps the user's own text but adds none of 0.1.0's (its *Your setup* section, the new modes, the reworded descriptions), so those parts of the page may end up shorter or gone; replace gives 0.1.0's whole page, and drops the user's own text outside `## Entries` (git history keeps it). Preselected: cut. To cut, run `--old-lines` again (a README row item 2 added moves the line numbers) and delete each listed line whole (in Markdown a line is a paragraph, a list item or a table row), then mend what that leaves broken: a heading with nothing under it, a table without its header row (delete the rest of that table), a numbered list's numbers, a kept sentence that points at a deleted line (reword it or delete it), and runs of blank lines. A line the user changed is theirs, and stays.
   - **`review:` an `outputs/` item outside 0.1.0's layout,** or a file left unchanged: where you would put it, or keep it. Preselected: yours.
4. Write the answers, then run the script again, without `--apply`. Repeat 2 to 4 until it prints `OK: nothing left to migrate`; a `review:` line the user chose to keep may stay, and a `migrate: poppler:` line is step 2's, so it may stay until then.
5. **Commit, on the user's yes.** This is a bulk change: show `git -C <root> status --short`, `git -C <root> diff --stat` and a short summary of what changed per file, and ask the user to read the full diff in their editor. On yes, restore a ` M tools/askpass-macos.sh` line as step 0 item 1 says, then `git -C <root> add -A -- <path>` each path `status --short` lists (a folder too, such as `stories/`; `outputs` for moved outputs), commit as `upgrade: Log formats to 0.1.0`, and push. On no, apply what they ask, then show the status and stat again.

Done when the script prints `OK: nothing left to migrate` (or only step 2's `migrate: poppler:` line), and the commit is pushed (`git -C <root> status --short` prints nothing).

## 4. Settings 0.1.0 adds

0.1.0 keeps the settings that were lines in `direction.md` in two places: Direction (what the user wants) stays in `direction.md`, and Config (how the Engine runs for this Log) is `config.toml`, which step 3 wrote with defaults, or 0.1.0's setup wrote before the upgrade. Config has fields the old Template had no line for: `interviewer_profiles`, `front_page`, and the scan mode's fields.

Start the setup mode (`skills/career-log/modes/setup.md`) on its *Advanced* path: `<py> -I <root>/tools/check.py setup` (the *Trigger check*; the *Start check*'s pull was step 0's), then its *Advanced* steps. Where the setup mode and this guide differ, this guide wins: on a Mac where step 2 item 1 ended with `OK:`, setup opens no dialog, so its notice about dialogs is for Windows only; and in *Advanced* step 3, a `next: now, for playwright-cli` line saying `(the user declined playwright-cli)` is left as it is (it installs only when the user asks). It shows every Config field and Direction item with its current value, and the user changes what they want. `config.py init` writes every field into `config.toml`, so `config.py show` marks none `(default)`. When step 3 wrote `config.toml`, tell the user that every field is at its default, except `record_language` when step 3 set it; when 0.1.0's setup wrote it, the values are that setup's answers, with any `record_language` step 3 set. In *Advanced* step 3, a `next: now, for tinytex` line with `pdftotext: missing` is step 2's poppler, handled as step 2's *When the check fails* says, not a setup run. Of the fields, tell them in particular about `interviewer_profiles` (whether interview prep may read interviewer profiles only signed-in members can see) and `front_page` (`trimmed` turns the front page into a personal index of their records).

Done when setup's *Advanced* close holds: every item the user changed is written and committed (no commit when they changed nothing: `config.toml` is already committed, by step 3 or before the upgrade).

## 5. Check

1. `<py> -I <root>/tools/check.py setup` and `<py> -I <root>/tools/check.py log`: no `config: missing` or `log change:` line, and in each the last line is `next: go on with the mode` and every other `next:` line is a `next: now, for playwright-cli` line saying `(the user declined playwright-cli)`. Any other `next:` line (`next: now, for tinytex` when poppler is missing) fails this item: go back to step 2. A `config: missing` line on a machine other than the one that ran step 3 means the upgrade has not reached this clone: `git -C <root> pull --ff-only`.
2. `<py> -I <root>/tools/entries.py check <root>`: no `no README row` or `README row` finding.
3. `<py> -I <root>/.build/upgrade/upgrade-0.1.0.py <root>`: `OK: nothing left to migrate`.
4. Tell the user what is left for later, from the script's `later:` lines and 0.1.0's own rules; none of it stops a mode:
   - **At the next consolidate** of each entry: `links:` keeps only repo roots and main sites (a PR, issue or commit is cited in the body), `## Past phrasings` lines in other old forms are rewritten, the entry is trimmed to what outputs use, and an entry over the size threshold (`entry over threshold`) is split into a series. `tools/entries.py check` names the entries over the threshold and the ongoing ones not updated for two months. A `## Log` section becomes `## Pending` at the next mode that edits the entry.
   - **Stories:** `stories.md` can now mark 3 to 5 core stories `*(core)*`, and the stories mode saves Talking points in `stories/`.
   - **`.export-deny`** matters only when this Log exports a Template of its own: the import, log and consolidate modes add names to it from now on. The `later:` line's count can grow in step 3, since a moved application folder's name is read as a recorded name.
   - **poppler, on a Mac:** if it goes missing later, 0.1.0's check says to run setup, which would install Homebrew. Instead, download the script again (step 0 item 2) and run `--poppler` (step 2 item 1).
5. Delete `<root>/.build/upgrade/`.

Done when items 1 to 3 hold, the user has heard item 4, and `<root>/.build/upgrade/` is gone.
